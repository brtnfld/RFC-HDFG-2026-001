\section{Parameter String Format}
\label{sec:param-format}

The parameter string format is based on TOML v1.0.0~\cite{toml10}, parsed by
a vendored subset of the tomlc17 library~\cite{tomlc17}.  The full TOML
v1.0.0 specification is the normative reference for syntax and value types;
this section documents the constraints imposed by the library and the
rationale for deviations.  Two usage profiles are defined: a tighter
\textbf{filter profile} for I/O filter configuration strings, and a more
permissive \textbf{VFD/VOL profile} for Virtual File Driver and VOL connector
configuration strings.

Using an established, externally maintained grammar provides typed values
(integer, float, boolean, string, array, inline table), a stable specification
the library does not need to own, and a path to nested configuration for VOL
connector and VFD stacks without changing the API or the wire format.

\subsection{Format Overview}
\label{sec:param-overview}

A parameter string is a comma-separated list of \texttt{key = value} pairs
conforming to the TOML inline table content grammar.  Outer braces are
\emph{optional}: the library accepts both the bare form
(\texttt{level = 6}) and the braced form (\texttt{\{level = 6\}}), wrapping
the string in \texttt{\{\ldots\}} internally before parsing if braces are
absent.  \texttt{NULL} or an empty string means ``no parameters'' and is
valid for filters that take no parameters (shuffle, fletcher32, nbit).

\verysubsection{Value types}

\begin{itemize}
\item \textbf{Integer:} Unquoted decimal integer, optional leading sign.
  Example: \texttt{level = 6}, \texttt{offset = -4}.
  TOML integer syntax (underscores as digit separators, \texttt{0x}/\texttt{0o}/\texttt{0b}
  prefixes) is accepted by the parser but filter callbacks receive the
  parsed \texttt{int64\_t} value directly via \texttt{H5Zconfig\_get\_int}.
\item \textbf{Float:} Unquoted decimal float with mandatory decimal point or
  exponent. Example: \texttt{rate = 3.5}, \texttt{tol = 1.0e-6}.
  The decimal separator is always a period regardless of locale.
  TOML special float values (\texttt{inf}, \texttt{nan}) are accepted by the
  parser but rejected with \texttt{H5E\_BADVALUE} by the library before
  \texttt{set\_config} is invoked.
  Hexadecimal float literals in C99 \texttt{\%a} form
  (e.g., \texttt{rate = 0x1.8p+1} for exactly \texttt{3.0}) are also accepted
  as input; the library rewrites them to decimal before the TOML scanner.
  The canonical output form produced by the library is \texttt{\%.17e}
  (\SectionRef{sec:float-precision}).
\item \textbf{Boolean:} \texttt{true} or \texttt{false} (lowercase only, per
  TOML).  The values \texttt{True}, \texttt{False}, \texttt{1}, and \texttt{0}
  are \emph{not} recognized as booleans; the parser rejects them with
  \texttt{H5E\_BADVALUE}.  Example: \texttt{fast\_mode = true}.
\item \textbf{String:} Double-quoted only (\texttt{"\ldots"}).  Standard TOML
  escape sequences are supported (\texttt{\textbackslash n}, \texttt{\textbackslash t},
  \texttt{\textbackslash\textbackslash}, \texttt{\textbackslash"}, etc.).
  Example: \texttt{coding = "entropy"}, \texttt{path = "/data/run\_1"}.
  Single-quoted TOML literal strings (\texttt{'\ldots'}) are also accepted;
  no escape processing is performed inside single quotes.
  An empty quoted value (\texttt{key = ""} or \texttt{key = ''}) is valid
  and passes the empty string to the filter callback; it is the filter's
  responsibility to accept or reject an empty value.
  A bare \texttt{key=} with no value and no quotes is a parse error and is
  rejected with \texttt{H5E\_BADVALUE}.
\item \textbf{Inline table (nested):} A value may itself be a
  comma-separated list of key=value pairs enclosed in braces.
  Example: \texttt{stripe = \{size = 1048576, count = 4\}}.
  Nesting is appropriate for VOL connector and VFD configuration, and
  also for filters that wrap a sub-compressor with its own parameters
  (e.g., Blosc selecting an internal compressor:
  \texttt{compressor = \{name = "zlib", level = 6\}, shuffle = 1}).
  Dotted-key form (\texttt{compressor.name = "zlib", compressor.level = 6})
  is equivalent and is the recommended style for readability in a
  single-line string.
\end{itemize}

\verysubsection{Keys}

Keys follow the TOML bare-key rules: ASCII letters, digits, hyphens, and
underscores (\texttt{[A-Za-z0-9\_-]+}).  Quoted keys (\texttt{"key"}) are
accepted by the parser but discouraged.  Keys are \emph{case-insensitive};
the library normalizes to lowercase before lookup.  Dotted keys
(\texttt{stripe.size}) are accepted and express one level of nesting
(\texttt{stripe.size = 1048576} is equivalent to
\texttt{stripe = \{size = 1048576\}}); they are the recommended form for
VOL/VFD nested parameters as they are more readable in a single-line string.
Duplicate keys are rejected with \texttt{H5E\_BADVALUE}.

\verysubsection{Additional constraints — filter profile}

The following constraints apply to parameter strings used with I/O filters
(i.e., strings passed to \texttt{H5Pappend\_filter} and the associated
\texttt{set\_config}/\texttt{get\_config} callbacks).

\begin{itemize}
\item \textbf{Maximum string length:} \texttt{H5Z\_CONFIG\_STRING\_MAX} (= 4096
  bytes).  Strings exceeding this limit are rejected with
  \texttt{H5E\_BADVALUE}.
\item \textbf{Maximum parameter count:} \texttt{H5Z\_CONFIG\_MAX\_PARAMS} (= 64
  top-level keys).  Strings containing more top-level keys are rejected with
  \texttt{H5E\_BADVALUE}.  This bound limits parsing work and exposure to
  maliciously crafted strings.
\item \textbf{Special float values:} \texttt{inf}, \texttt{-inf}, and
  \texttt{nan} are valid TOML but rejected by the library with
  \texttt{H5E\_BADVALUE}.
\item \textbf{TOML features not supported:} Arrays (\texttt{[1,2,3]}),
  multi-line strings, datetime values, and document-level tables
  (\texttt{[section]}) are not part of the filter profile.  The parser
  rejects them with \texttt{H5E\_BADVALUE}.
\item \textbf{Locale independence:} The parser and all typed accessors use
  C-locale numeric conversion.  Process-wide locale settings do not affect
  parsing.  The decimal separator is always a period.
\end{itemize}

\verysubsection{Floating-point precision and serialization}
\label{sec:float-precision}

Decimal float literals are convenient for humans but cannot represent all
IEEE\,754 \texttt{double} values exactly.  A value such as \texttt{rate = 0.1}
parses to the nearest representable double, which when re-serialized as a
decimal string may produce a slightly different numeral.  Passing such a
reconstructed string back to \texttt{set\_config} may therefore yield a
different binary value, breaking compression reproducibility.

Because the configuration string is persisted on disk
(\SectionRef{sec:pline-v3}), serialization precision is \emph{not}
load-bearing for round-trip fidelity of string-configured pipelines: what
the user typed is what introspection returns.  The requirements in this
subsection govern the remaining places where the library or a callback
\emph{produces} a float numeral --- chiefly \texttt{get\_config}
reconstruction for entries that carry no stored string
(\SectionRef{sec:introspection}) --- so that those strings, too, round-trip
exactly when fed back to \texttt{set\_config}.

\textbf{Input (accepted by the library):} Both decimal float literals
(e.g., \texttt{rate = 3.5}) and C99 hexadecimal float literals
(e.g., \texttt{rate = 0x1.cp+1}) are valid in parameter strings.
The library pre-processes hex-float tokens into equivalent decimal form
before the TOML scanner, so hex-float input does not require TOML~v1.0
compliance from the underlying parser.

\textbf{Output (produced by the library and callbacks):} \texttt{get\_config}
implementations \emph{shall} format \texttt{float} and \texttt{double} values
using \texttt{\%.17e}.  This format:
\begin{itemize}
  \item always emits a decimal point and exponent (e.g.\ \texttt{3.00000000000000000e+00}),
    satisfying the TOML~v1.0 requirement that float literals contain a
    \texttt{.} or an exponent --- \texttt{\%.17g} is \emph{not} used because
    it drops the decimal point for whole numbers (\texttt{8.0}~$\to$~\texttt{"8"}),
    which TOML parsers interpret as an integer;
  \item guarantees exact IEEE\,754 double round-trips: C99 \texttt{DBL\_DECIMAL\_DIG}
    is 17, meaning 17 significant decimal digits suffice to distinguish any two
    distinct \texttt{double} values and recover the original bit pattern via
    \texttt{strtod}; and
  \item is made locale-independent by the implementation: standard
    \texttt{snprintf} respects \texttt{LC\_NUMERIC} and may replace the decimal
    point with a comma (e.g., \texttt{de\_DE} locale), which TOML prohibits.
    Implementations must therefore scan the formatted string and replace any
    comma with a period before use; since \texttt{\%.17e} places exactly one
    decimal separator in the mantissa, a single-pass scan suffices.
\end{itemize}

\begin{notebox}
\textbf{Implementation requirements:}
\begin{itemize}
  \item \textbf{Parser:} The library pre-processes hex-float tokens
    (e.g., \texttt{0x1.8p+1}) into \texttt{\%.17e} decimal form before the
    TOML scanner.  No changes to the vendored tomlc17 subset are required.
  \item \textbf{\texttt{get\_config} callbacks:} Use \texttt{\%.17e} for all
    \texttt{float} and \texttt{double} values in parameter strings.  Do not
    use \texttt{\%g}, \texttt{\%f}, \texttt{\%a}, or fewer than 17 significant
    digits.  Document this requirement in \texttt{H5Zdevelop.h} as a normative
    requirement for third-party plugins.
  \item \textbf{Documentation:} Add a note to \texttt{H5Zdevelop.h} and the
    plugin author guide explaining the \texttt{\%.17e} requirement and why
    \texttt{\%.17g} is insufficient.
\end{itemize}
\end{notebox}

\verysubsection{Additional constraints — VFD/VOL profile (future work)}

\begin{outofscope}
VFD/VOL configuration is out of scope for this RFC.  The constraints below
are forward-looking design notes included for completeness.
\end{outofscope}

VFD and VOL connector configuration strings require richer structure than
filter parameter strings: arbitrary stack depth, arrays (e.g., lists of
endpoint addresses), and file-based delivery that benefits from multi-section
TOML documents.  The following relaxed constraints apply to parameter strings
used in VFD and VOL connector configuration contexts.

\begin{itemize}
\item \textbf{Full TOML v1.0.0 document syntax supported:} Arrays
  (\texttt{[1,2,3]}), multi-line strings, and document-level tables
  (\texttt{[section]}) are all accepted.
\item \textbf{Arbitrary nesting depth:} Inline tables and dotted keys may be
  nested to any depth required to express the VFD stack hierarchy.  There is
  no library-imposed depth limit beyond available stack memory.
\item \textbf{Maximum string length:} \texttt{H5FD\_CONFIG\_STRING\_MAX} (=
  16384 bytes).  A full multi-level VFD stack with a SWMR configuration group
  is unlikely to exceed a few kilobytes; 16\,KB provides ample headroom.
  Strings exceeding this limit are rejected with \texttt{H5E\_BADVALUE}.
\item \textbf{Maximum top-level key count:} \texttt{H5FD\_CONFIG\_MAX\_PARAMS}
  (= 256).  Strings containing more top-level keys are rejected with
  \texttt{H5E\_BADVALUE}.
\item \textbf{Special float values:} \texttt{inf}, \texttt{-inf}, and
  \texttt{nan} are rejected with \texttt{H5E\_BADVALUE}, consistent with the
  filter profile.
\item \textbf{Locale independence:} C-locale numeric conversion applies, as
  in the filter profile.
\end{itemize}

The VFD name is expressed as the sole top-level key, with its configuration
parameters as the value (an inline table or dotted keys).  An underlying VFD
in a stack is expressed as a nested key under the outer VFD's table.  An
empty parameter list is expressed as an empty inline table (\texttt{\{\}}).
For example, a three-level page-buffer~$\to$~encryption~$\to$~sec2 stack:

\begin{minted}{toml}
page_buffer.page_size       = 4096
page_buffer.max_num_pages   = 64
page_buffer.underlying_vfd.encryption_vfd.plaintext_page_size = 4096
page_buffer.underlying_vfd.encryption_vfd.key = "0123456789ABCDEF..."
page_buffer.underlying_vfd.encryption_vfd.underlying_vfd.sec2 = {}
\end{minted}

or equivalently as inline tables:

\begin{minted}{toml}
page_buffer = {
  page_size = 4096, max_num_pages = 64,
  underlying_vfd = { encryption_vfd = {
    plaintext_page_size = 4096, key = "0123456789ABCDEF...",
    underlying_vfd = { sec2 = {} }
  }}
}
\end{minted}

\subsection{VFD/VOL Profile: Use Case Coverage (Future Work)}
\label{sec:vfd-use-cases}

\begin{outofscope}
This subsection is out of scope for this RFC.  It is included as
forward-looking design context to demonstrate that the TOML grammar chosen
for filter configuration extends naturally to VFD and VOL connector
configuration.  The API changes described here
(\texttt{H5FDconfig\_get\_subtable\_str}, \texttt{H5FDconfig\_load\_from\_file},
VFD/VOL profile constants) are not part of this RFC.
\end{outofscope}

This subsection demonstrates, use case by use case, that the TOML VFD/VOL
profile is sufficient to express all VFD stack configuration requirements.
The Lifeboat VFD configuration RFC~\cite{lifeboat-vfd-cl} provides a concrete
set of use cases and motivates several of the design choices described hereafter.

\verysubsection{UC-1: Flat scalar VFD parameters}

\textbf{Use case.}  A VFD such as the page buffer VFD requires a small set of
scalar parameters: page size, maximum number of pages, replacement policy.

\textbf{Coverage.}  Standard TOML key\,=\,value pairs cover this
directly.  The grammar provides typed integers, floats, booleans, and quoted
strings without any extension.  Example:

\begin{minted}{toml}
page_buffer = { page_size = 4096, max_num_pages = 64, replacement_policy = 0 }
\end{minted}

No aspect of this use case requires any relaxation beyond ordinary TOML.

\verysubsection{UC-2: Boolean flags}

\textbf{Use case.}  VFD SWMR configuration contains several boolean fields
(e.g., \texttt{presume\_posix\_semantics}, \texttt{flush\_raw\_data}).  The
Lifeboat grammar has no boolean type; it uses integer \texttt{0}/\texttt{1}
as a workaround, requiring comment annotations (\texttt{/* <- Use integer for
bool value */}) to explain the intent.

\textbf{Coverage.}  TOML has a native boolean type:
\texttt{true}/\texttt{false} (lowercase, unquoted).  The intent is
self-documenting and the parser enforces the type without integer-to-boolean
coercion.  Example:

\begin{minted}{toml}
H5F_vfd_swmr_config = {
  presume_posix_semantics = true,
  flush_raw_data          = true,
  generate_updater_files  = false
}
\end{minted}

Native boolean support eliminates the need for integer \texttt{0}/\texttt{1} workarounds.

\verysubsection{UC-3: Binary blob values (e.g., encryption keys)}

\textbf{Use case.}  The encryption VFD requires a raw binary key (32 bytes in
the Lifeboat example).  The Lifeboat grammar introduces a special
\texttt{<binary\_blob>} terminal with a \texttt{--} prefix to distinguish hex
byte sequences from identifiers and integers.

\textbf{Coverage.}  TOML has no native binary type, but a quoted
string carrying a hex-encoded value is fully sufficient.  The VFD callback
receives the string and decodes it.  The convention is explicit and requires no
grammar extension:

\begin{minted}{toml}
encryption_vfd = {
  key = "0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF"
}
\end{minted}

TOML's quoted string type carries arbitrary content, so no disambiguation
prefix is needed.  The decoding convention (e.g., hex, base64) is specified
by the VFD and validated in its configuration entry point, as with all other
parameter types.

\textbf{Validation responsibility.}  In the Lifeboat grammar, the parser
natively enforces that a \texttt{<binary\_blob>} terminal contains only valid
hex characters.  Under TOML the parser treats the value as an opaque string;
it is therefore the VFD's responsibility to validate the string's content
(character set, byte length, encoding) and return \texttt{H5E\_BADVALUE} if
the value is malformed.  This is the same responsibility pattern already
required of all other parameter types: the TOML grammar validates syntax and
type, while semantic validation (range checks, format checks) belongs to the
VFD.  The shift is in degree, not in kind.

\verysubsection{UC-4: Arbitrary-depth VFD stack nesting}

\textbf{Use case.}  A VFD stack may contain three or more levels (e.g.,
page buffer~$\to$~encryption~$\to$~sec2).  Each VFD must be able to read its
own parameters and forward the remaining configuration to the underlying VFD,
without any VFD needing to know the schema of its neighbors.

\textbf{Coverage.}  TOML inline tables and dotted keys are
recursively defined and support arbitrary nesting depth.  The VFD/VOL profile
removes any library-imposed depth limit.  Each VFD in the stack reads the
keys it recognizes by name and extracts the \texttt{underlying\_vfd} sub-table
to pass to the next level.  Because TOML keys are named rather than
positional, each VFD looks up only what it knows about and ignores everything
else; no VFD needs visibility into any other VFD's schema.

The full three-level example from UC-1:

\begin{minted}{toml}
page_buffer = {
  page_size = 4096, max_num_pages = 64,
  underlying_vfd = { encryption_vfd = {
    plaintext_page_size = 4096, key = "...",
    underlying_vfd = { sec2 = {} }
  }}
}
\end{minted}

The page buffer VFD reads \texttt{page\_size} and \texttt{max\_num\_pages},
then calls \texttt{H5FDconfig\_get\_subtable\_str} to extract the
\texttt{underlying\_vfd} value as a raw TOML string
(\SectionRef{sec:subtable-extraction}), creates a new FAPL, and loads that
string into the FAPL's \texttt{driver\_config\_str} field via
\texttt{H5FDconfig\_load\_str\_into\_fapl}.  The encryption VFD
receives that FAPL, reads its own keys from the extracted string, and
similarly forwards the \texttt{underlying\_vfd.sec2} sub-table to the sec2
configuration.  No VFD ever parses keys belonging to another VFD.

\textbf{API note.}  VFDs do not use the \texttt{H5Z\_class3\_t.set\_config}
callback defined in \SectionRef{sec:class3}; that callback is specific to I/O
filters.  VFD configuration strings are delivered via the
\texttt{driver\_config\_str} field of \texttt{H5FD\_driver\_prop\_t} (defined
in \texttt{H5FDprivate.h}), which is already present in the HDF5 library.
The TOML VFD/VOL profile described here specifies the \emph{format} of that
string; no change to the \texttt{H5FD\_class\_t} struct or the VFD open
callback signature is required by this RFC.

\verysubsection{UC-5: VFD name as the top-level identifier}

\textbf{Use case.}  In the Lifeboat grammar, the VFD name is the outer
identifier of the top-level name-value pair: \texttt{( page\_buffer ( \ldots )
)}.  The configuration string is self-describing: the consumer can determine
which VFD is being configured without out-of-band information.

\textbf{Coverage.}  The same self-describing property is achieved
by convention: the VFD name is the sole top-level key, and its value is the
parameter table.  A configuration string that begins with
\texttt{page\_buffer~=~\{~\ldots~\}} unambiguously identifies the page buffer
VFD as the top-level driver.  The library reads the top-level key name to
determine which VFD to load and configure.

\textbf{Sole top-level key enforcement.}  The library validates that a
VFD/VOL profile configuration string contains \emph{exactly one} top-level
key.  If zero top-level keys are present the string is treated as ``no
configuration'' (equivalent to a \texttt{NULL} string).  If two or more
top-level keys are present (e.g., \texttt{page\_buffer = \{\ldots\}, sec2 =
\{\}}) the library returns \texttt{H5E\_BADVALUE} immediately, before
consulting any VFD.  This rule ensures unambiguous driver identification and
mirrors the Lifeboat grammar's constraint that the top-level is always a
single \texttt{<name\_value\_pair>}.

\verysubsection{UC-6: Empty parameter list}

\textbf{Use case.}  The sec2 VFD requires no configuration parameters.  In
the Lifeboat grammar this is expressed as \texttt{( sec2 () )} --- a VFD name
with an explicit but empty parameter list.

\textbf{Coverage.}  An empty inline table \texttt{sec2 = \{\}} is
the direct and idiomatic equivalent.  The VFD name is present (self-describing),
the parameter list is explicitly empty, and the grammar requires no special
case.  \texttt{NULL} or an empty string is also accepted by the VFD/VOL
profile and treated as ``no parameters'', consistent with the filter profile.

\verysubsection{UC-7: Configuration groups (VFD SWMR)}

\textbf{Use case.}  VFD SWMR requires coordinated configuration across
multiple subsystems: the SWMR engine itself, the page buffer, file space
strategy, and file space page size.  Historically these were configured
independently, risking writer/reader mismatches.  The Lifeboat RFC introduces
a ``configuration group'' concept: a named outer wrapper containing multiple
named sub-configurations that are parsed and applied together.

\textbf{Coverage.}  The configuration group maps directly onto a
TOML table whose value is a list of named sub-tables.  When delivered as an
inline string (e.g., environment variable or API call), nested inline tables
express the group:

\begin{minted}{toml}
vfd_swmr_config_data = {
  H5F_vfd_swmr_config = {
    version = 1, tick_len = 4, max_lag = 7,
    presume_posix_semantics = true, flush_raw_data = true,
    md_file_path = "./md_dir", md_file_name = "md_file"
  },
  page_buffer_config = {
    page_buf_size = 4096, metadata_pages_only = true
  },
  file_space_strategy_config = { persist = false },
  file_space_page_size        = { page_size = 4096 }
}
\end{minted}

When delivered from a file, standard TOML document-level section tables are
the natural form (permitted under the VFD/VOL profile):

\begin{minted}{toml}
[vfd_swmr_config_data.H5F_vfd_swmr_config]
version   = 1
tick_len  = 4
max_lag   = 7
presume_posix_semantics = true
flush_raw_data          = true
md_file_path = "./md_dir"
md_file_name = "md_file"

[vfd_swmr_config_data.page_buffer_config]
page_buf_size       = 4096
metadata_pages_only = true

[vfd_swmr_config_data.file_space_strategy_config]
persist = false

[vfd_swmr_config_data.file_space_page_size]
page_size = 4096
\end{minted}

Both forms parse to the same TOML AST and express identical configuration
data.  However, they are not processed identically at the library level: an
inline string is stored verbatim in the FAPL's \texttt{driver\_config\_str}
and consumed directly by VFDs, while a file containing document-level section
tables is first parsed and normalized to an inline string by the
file-loading helper (\SectionRef{sec:subtable-extraction}) before being
placed in the FAPL.  VFDs always see the inline form; the distinction between
the two authoring styles is transparent to them.

The top-level name (\texttt{vfd\_swmr\_config\_data}) identifies the
configuration group, and each sub-table name identifies the target subsystem.
The writer/reader coordination
problem is solved by the same mechanism: both sides load from the same
configuration string or file, with the library applying writer- and
reader-specific flag overrides (\texttt{writer}, \texttt{create\_file})
programmatically rather than encoding them in the configuration string.

\verysubsection{UC-8: Stack-level delegation without breadth-first parsing}

\textbf{Use case.}  The Lifeboat grammar was designed around a
\emph{breadth-first} parsing model: when a VFD encounters the configuration
string, it parses only its own parameters and receives the sub-expression for
the underlying VFD as a single opaque token, which it passes down the stack
unchanged.  The motivation, as stated in the Lifeboat RFC, is schema
isolation: each VFD in the stack should not need to know anything about the
configuration data for the underlying VFDs.  This is achieved by a
context-sensitive lexer that, when a name-value pair value is expected,
treats a parenthesised sub-expression as a single token rather than
descending into it.  Each VFD parses only the keys at its own level and
forwards the unparsed sub-expression string down the stack.

\textbf{Schema isolation via AST lookup.}  TOML parsers (including the
vendored tomlc17 subset) build a full recursive AST in a single pass, after
which each VFD can locate the keys it recognises by name and extract the
\texttt{underlying\_vfd} sub-table without scanning past unknown structure.
Schema isolation is preserved --- each VFD reads only its own keys --- through
named-key lookup over a complete AST.

\textbf{Implementation.}  Each VFD in the stack receives a TOML configuration
string via \texttt{driver\_config\_str} in its FAPL.  It parses that string,
extracts its own keys by name using \texttt{H5FDconfig\_get\_*} helpers, then
calls \texttt{H5FDconfig\_get\_subtable\_str} (\SectionRef{sec:subtable-extraction})
to extract the raw source bytes of the \texttt{underlying\_vfd} value — no
AST-to-string serialization is required, because the helper works directly on
the original input bytes.  The extracted substring is loaded into a new FAPL's
\texttt{driver\_config\_str} and passed to the next VFD's open callback.
Configuration strings are small (well under the 16\,KB VFD/VOL profile limit),
so the substring extraction overhead is negligible.  Each VFD independently
validates and consumes only its own configuration data, achieving full schema
isolation without any special parsing protocol.

\subsection{Parser Implementation}
\label{sec:param-parser}

The parameter string parser is a vendored, reduced subset of
tomlc17~\cite{tomlc17}, a MIT-licensed C17 TOML library.  The vendored
copy lives under \texttt{src/H5Ztoml.\{c,h\}} and is stripped to the inline
table and primitive value subset described in \SectionRef{sec:param-overview}.
HDF5's memory allocation functions (\texttt{H5MM\_malloc} etc.)\ are
substituted for the library's default allocator.  The vendored copy is
updated as part of the normal HDF5 dependency refresh process; the TOML
v1.0.0 grammar is stable and no API-breaking changes are expected.

The semicolon character is reserved at the grammar level for a possible
future pipeline-string extension (\texttt{"shuffle; deflate, level = 9;
fletcher32"}); it is not part of the TOML inline table grammar and is
rejected with \texttt{H5E\_BADVALUE} outside of quoted strings.

\verysubsection{Sub-table string extraction for VFD stack delegation (future work)}
\label{sec:subtable-extraction}

\begin{outofscope}
Out of scope for this RFC.  See \SectionRef{sec:vfd-use-cases}.
\end{outofscope}

VFD stack delegation (\SectionRef{sec:vfd-use-cases}, UC-4 and UC-8) requires
a VFD to pass the configuration of its underlying VFD as a string to that
VFD's configuration entry point.  Because the \texttt{set\_config} entry point
accepts a \texttt{const char~*} string, a VFD cannot pass a parsed
\texttt{toml\_table\_t} pointer directly to the next level.

Standard C TOML parsers, including tomlc17, build an in-memory parse tree but
do not include an emitter to serialize that tree back to a string.  Rather
than adding a full TOML emitter to the vendored library---which would
significantly increase complexity and maintenance burden---the library instead
provides a lightweight helper function that extracts the raw source substring
corresponding to a named sub-table directly from the original input string:

\begin{minted}{c}
herr_t H5FDconfig_get_subtable_str(
    const char  *params,      /* original VFD config string          */
    const char  *key,         /* dotted key path, e.g. "underlying_vfd" */
    char        *buf,         /* output buffer, or NULL for size query   */
    size_t      *buf_size     /* in: capacity; out: required length      */
);
\end{minted}

This function locates the value span of \texttt{key} in \texttt{params} by
scanning the source bytes directly (using the same lexer used by the parser
to identify balanced brace extents), copies the raw substring into
\texttt{buf}, and returns its length via \texttt{buf\_size}.  The extracted
substring is a valid TOML inline table string that the receiving VFD can
parse independently.  This approach:

\begin{itemize}
\item Requires no emitter and no AST traversal beyond balanced-brace matching.
\item Preserves the exact source text, including whitespace and comments,
  avoiding any round-trip fidelity issues.
\item Follows the standard HDF5 size-query pattern: passing \texttt{NULL} for
  \texttt{buf} returns the required buffer size without copying.
\item Returns \texttt{H5E\_NOTFOUND} if the key is absent, and
  \texttt{H5E\_BADVALUE} if the value is not a table (i.e., is a scalar).
\end{itemize}

\textbf{Inline table requirement.}
\texttt{H5FDconfig\_get\_subtable\_str} operates on inline table syntax only.
Balanced-brace scanning works because the value of a named key in an inline
table is always a contiguous, brace-delimited span in the source bytes.
Document-level section tables (\texttt{[section]}) have no such span: the
keys of \texttt{[page\_buffer.underlying\_vfd]} are scattered across the file
with no enclosing braces, so there is no contiguous substring to extract.

This is not a limitation in practice because document-level tables
\emph{never reach \texttt{driver\_config\_str} directly}.  The two delivery
paths are:

\begin{enumerate}
\item \textbf{Inline string} (environment variable, API call): the caller
  supplies an inline table string, which is stored verbatim in
  \texttt{driver\_config\_str}.  \texttt{H5FDconfig\_get\_subtable\_str}
  operates on this string directly.
\item \textbf{File-based delivery}: the application calls a library helper
  such as \texttt{H5FDconfig\_load\_from\_file()} (analogous to the Lifeboat
  \texttt{H5CL\_load\_config\_string\_from\_file()}), which reads the file,
  parses it into a TOML AST (accepting document-level tables in that parse),
  and then emits a single normalized inline table string that it stores in
  the FAPL's \texttt{driver\_config\_str}.  From that point on, all VFDs in
  the stack see only the inline form.
\end{enumerate}

The document-level \texttt{[section]} syntax is therefore a user-facing
authoring convenience.  The library's file-loading helper is the single point
responsible for normalizing it to inline form; \texttt{H5FDconfig\_get\_subtable\_str}
and all downstream VFD configuration logic operate exclusively on inline
strings.  The normalization step requires the file-loading helper to include a
minimal inline-table emitter, scoped only to that one helper and not exposed
to VFD authors.

This function is defined in \texttt{H5FDconfig.c} and declared in
\texttt{H5FDdevelop.h}, placing it in the VFD developer API rather than the
filter developer API (\texttt{H5Zdevelop.h}).  The \texttt{H5FD} prefix
distinguishes it from the filter-scoped \texttt{H5Zconfig\_*} helpers.

\begin{outofscope}
\texttt{H5FDconfig\_get\_subtable\_str} and the associated
\texttt{H5FDconfig\_load\_from\_file} helper are not part of this RFC and are
not present in the HDF5 source tree.
\end{outofscope}

\section{Filter Plugin Class Version 3}
\label{sec:class3}

\subsection{Rationale}

Version~3 of the filter class extends \texttt{H5Z\_class2\_t} in two
ways:

\begin{enumerate}
\item \textbf{String configuration callbacks} (\texttt{set\_config},
  \texttt{get\_config}) --- a filter can accept a human-readable
  key--value parameter string and, optionally, reconstruct it for
  introspection.

\item \textbf{Extended filter callback} --- the filter function used by
  \texttt{H5Z\_class3\_t} receives the active data-transfer property list
  (\texttt{dxpl\_id}) and the chunk's scaled coordinates (\texttt{scaled},
  \texttt{ndims}) as additional parameters at I/O time, enabling access to
  non-serializable runtime handles and spatially-aware compression.
\end{enumerate}

\subsection{Version Numbering}
\label{sec:version-numbering}

The existing version-to-struct mapping in HDF5 is:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Struct} & \textbf{Version Field} \\
\midrule
\texttt{H5Z\_class1\_t} & none (legacy) \\
\texttt{H5Z\_class2\_t} & \texttt{1} \\
\texttt{H5Z\_class3\_t} & \texttt{2} \\
\bottomrule
\end{tabular}
\end{center}

The version field is a single, monotonically increasing integer shared
across all class struct generations.  Plugin authors set this field to the
literal value corresponding to their chosen struct (\texttt{1} for
\texttt{H5Z\_class2\_t}, \texttt{2} for \texttt{H5Z\_class3\_t}).  Adding a
future \texttt{H5Z\_class4\_t} would assign it value \texttt{3}, with no new
per-struct version macro required.

The version constants are:

\begin{minted}{c}
#define H5Z_CLASS_T_VERS      1   /* Unchanged -- existing constant for H5Z_class2_t  */
#define H5Z_CLASS_T_VERS_MAX  2   /* Highest accepted version field value (currently  *
                                   * H5Z_class3_t).  Used by the library for sanity   *
                                   * checking; plugin authors should not reference it *
                                   * directly, since its value increases as new       *
                                   * struct generations are added.                    */
\end{minted}

\texttt{H5Z\_CLASS\_T\_VERS} remains at \texttt{1} for backward compatibility
with code that already references it; \texttt{H5Z\_class3\_t} plugin authors
set the field to the literal value \texttt{2}, per the dispatch logic below.
\texttt{H5Z\_CLASS\_T\_VERS\_MAX} is reserved for library sanity checking and
should not be referenced by plugin authors directly, since its value increases as
new struct generations are added. The library's internal dispatch in
\texttt{H5Z.c} uses its own package-private constant, pinned to \texttt{2}
independent of \texttt{H5Z\_CLASS\_T\_VERS\_MAX}.

\textbf{Future class versions:} Other in-progress HDF5 work (e.g.,
Accelerator-native I/O Pipeline) may also need to extend
\texttt{H5Z\_class\_t}.  The \texttt{H5Z\_CLASS\_T\_VERS\_MAX} pattern
accommodates this without back-to-back struct versioning: a future
\texttt{H5Z\_class4\_t} would set \texttt{version = 3} and
\texttt{H5Z\_CLASS\_T\_VERS\_MAX} would be bumped to \texttt{3} in the same
release, with a new dispatch branch added for \texttt{version == 3}.
Extensions to \texttt{H5Z\_class\_t} from different features should be
merged in the same release to avoid consecutive struct-generation bumps.

The dispatch logic in \texttt{H5Zregister()} currently works by checking
\texttt{version != H5Z\_CLASS\_T\_VERS} first; any other value is treated as a
legacy \texttt{H5Z\_class1\_t} struct.  The dispatch is extended to recognise
\texttt{version == 2} as \texttt{H5Z\_class3\_t}, with
\texttt{H5Z\_CLASS\_T\_VERS\_MAX} guarding against unknown future values:

\begin{minted}{c}
    if (version > H5Z_CLASS_T_VERS_MAX)
        /* -> error: version field exceeds library support */
    else if (version == H5Z_CLASS_T_VERS)  /* 1 */
        /* -> H5Z_class2_t        */
    else if (version == 2)
        /* -> H5Z_class3_t        */
    else
        /* -> legacy H5Z_class1_t */
\end{minted}

Note: When \texttt{H5\_NO\_DEPRECATED\_SYMBOLS} is defined, the legacy
\texttt{H5Z\_class1\_t} path is compiled out entirely and any value other
than \texttt{H5Z\_CLASS\_T\_VERS} or \texttt{2} produces a hard error.  Under
\texttt{H5\_NO\_DEPRECATED\_SYMBOLS}, only versions \texttt{1} and \texttt{2}
are accepted.

\texttt{H5Z\_class3\_t} is an independent flat struct; it does NOT embed
\texttt{H5Z\_class2\_t} as a member.  The library reads the \texttt{version}
field in \texttt{H5Zregister()} via \texttt{memcpy}
through a \texttt{char~*} to avoid strict-aliasing undefined behaviour.
\texttt{H5PL\_\_open} receives an already-typed pointer via the plugin's
exported \texttt{H5PLget\_plugin\_info()} symbol and does not need this.

Document the version-to-struct mapping table in \texttt{H5Zdevelop.h}.

\verysubsection{Compatibility macro in \texttt{H5version.h}}
The existing compatibility macro
(\texttt{H5version.h}) maps the generic type alias \texttt{H5Z\_class\_t} to a versioned
struct:

\begin{minted}{c}
#if !defined(H5Z_class_t_vers) || H5Z_class_t_vers == 2
  #define H5Z_class_t H5Z_class2_t
#elif H5Z_class_t_vers == 1
  #define H5Z_class_t H5Z_class1_t
#endif
\end{minted}

Currently \texttt{H5Z\_class\_t\_vers} defaults to \texttt{2}, mapping
\texttt{H5Z\_class\_t} $\rightarrow$ \texttt{H5Z\_class2\_t}. This macro is not changed to default to
\texttt{3} (mapping to \texttt{H5Z\_class3\_t}), because existing code using \texttt{H5Z\_class\_t}
would silently get the larger struct with uninitialized callback fields. The
default remains \texttt{2}. A new value of \texttt{3} can be added as an opt-in for
code that explicitly requests \texttt{H5Z\_class3\_t}:

\begin{minted}{c}
#if !defined(H5Z_class_t_vers) || H5Z_class_t_vers == 2
  #define H5Z_class_t H5Z_class2_t
#elif H5Z_class_t_vers == 1
  #define H5Z_class_t H5Z_class1_t
#elif H5Z_class_t_vers == 3
  #define H5Z_class_t H5Z_class3_t
#endif
\end{minted}

Plugin authors adopting v3 should use \texttt{H5Z\_class3\_t} directly rather than
relying on the \texttt{H5Z\_class\_t} alias.


\subsection{Structure Definition}
\label{sec:class3-struct}

\begin{minted}{c}
typedef herr_t (*H5Z_set_config_func_t)(
    const char   *params,
    unsigned     *flags,
    size_t       *cd_nelmts,
    unsigned      cd_values[],
    size_t        cd_values_size
);

typedef herr_t (*H5Z_get_config_func_t)(
    unsigned          flags,
    size_t            cd_nelmts,
    const unsigned    cd_values[],
    char             *buf,
    size_t           *buf_size
);

/* Extended filter callback for H5Z_class3_t.
 * Adds dxpl_id (active DXPL) and scaled[]/ndims (chunk coordinates)
 * to the existing H5Z_func_t parameter list.  H5Z_class2_t continues
 * to use H5Z_func_t; only class3 filters use this type. */
typedef size_t (*H5Z_func2_t)(unsigned int        flags,
                              size_t              cd_nelmts,
                              const unsigned int  cd_values[],
                              hid_t               dxpl_id,
                              const hsize_t      *scaled,
                              size_t              ndims,
                              size_t              nbytes,
                              size_t             *buf_size,
                              void              **buf);

typedef struct H5Z_class3_t {
    int                         version;
    H5Z_filter_t                id;
    unsigned                    encoder_present;
    unsigned                    decoder_present;
    const char                 *name;
    const char                 *description;
    H5Z_can_apply_func_t        can_apply;
    H5Z_set_local_func_t        set_local;
    H5Z_func2_t                 filter;    /* extended: dxpl_id + scaled */
    H5Z_set_config_func_t       set_config;
    H5Z_get_config_func_t       get_config;
} H5Z_class3_t;
\end{minted}

\verysubsection{Field descriptions}

\begin{itemize}
\item \texttt{name}---The same field as in \texttt{H5Z\_class2\_t}
  (same offset, same type, same lifetime).  In v3 the field's
  contract is strengthened: it is no longer a free-form ``debug
  comment'' but the filter's \emph{canonical name}---a short, stable,
  unique string identifier (e.g., \texttt{"zfp"}, \texttt{"blosc2"})
  that the filter uses to identify itself and that the library uses
  as the human-readable label.  It must not be \texttt{NULL} for v3
  plugins.  Plugin authors must treat the value as immutable and must
  not vary it across versions of the same plugin.  No struct member
  is renamed; the migration from v2 to v3 is purely a contract change
  on the contents of \texttt{name}.

  \textbf{Scope: plugin class, not algorithm variant.}  A filter plugin
  that supports multiple internal algorithms (e.g., Blosc2, which can use
  lz4, zstd, snappy, and others as its internal compressor) registers a
  single canonical name for the plugin class (\texttt{name = "blosc2"}).
  The choice of internal algorithm is a \emph{parameter}, expressed in
  the TOML configuration string (e.g., \texttt{"compressor=lz4,
  clevel=5"}), not a separate filter identity.

  \textbf{How it is stored and retrieved.}  When a v3 filter is appended
  to a pipeline, the library writes the plugin's \texttt{name} into the
  filter-pipeline message's name slot on disk.  This is the same slot
  v2 plugins have always used (the encoder at
  \texttt{H5O\_\_pline\_encode} reads \texttt{cls->name} and writes it
  to disk; the decoder at \texttt{H5O\_\_pline\_decode} reads it back
  into \texttt{filter->name}) and that \texttt{H5Pget\_filter2} has
  always returned via its \texttt{name[]} output parameter.  This RFC
  does not introduce a new persistence channel; it strengthens the
  contract on the bytes that channel carries.  The library does
  \emph{not} pack the name into \texttt{cd\_values}: the on-disk slot
  is the single source of persistence for the filter's display name,
  so v2 plugins on older libraries see exactly the \texttt{cd\_values}
  their own \texttt{set\_config} produced and the read-side
  legacy-plugin hazards that earlier drafts of this RFC described do
  not arise.

  When the plugin \emph{is} registered, \texttt{H5Pget\_filter2}
  returns \texttt{name} directly from the runtime registry; without
  the plugin, it falls back to the name persisted in the pipeline
  message; with neither available, it falls back to the numeric
  filter ID formatted as a decimal string.

  \textbf{Reading old files: non-canonical name content is harmless.}
  Files written before this RFC carry whatever string the v2 plugin
  author put into the \texttt{name} field, ranging from a one-word
  identifier to free-form prose to a NULL.  A v3-aware library
  reading such a file behaves as follows:

  \begin{itemize}
  \item \emph{If the corresponding v3 plugin is loaded:}
    \texttt{H5Pget\_filter2} returns the canonical \texttt{name}
    from the runtime registry; the on-disk slot is shadowed and its
    contents do not propagate anywhere.
  \item \emph{If only the v2 plugin is loaded:} \texttt{H5Pget\_filter2}
    returns the v2 plugin's \texttt{name} from the runtime registry,
    exactly as it did before this RFC.
  \item \emph{If no plugin is loaded:} \texttt{H5Pget\_filter2}
    returns the bytes from the on-disk slot verbatim, exactly as it
    did before this RFC.
  \end{itemize}

  In none of these cases does the library promote on-disk content to
  the runtime registry, treat it as a canonical identifier, or use
  it for a programmatic lookup.  The on-disk slot is one-way:
  display/introspection out, never an authoritative source in.

  \textbf{Consequence: no name$\rightarrow$ID lookup via the on-disk
  slot.}  Because the slot may carry pre-v3 free-form content, it is
  not a reliable reverse map from canonical name to numeric ID.  The
  future name-based lookup mechanism (\SectionRef{sec:future-name-lookup})
  resolves names by loading plugins and matching against
  \texttt{H5Z\_class3\_t.name} in the loaded plugin struct---never
  by consulting on-disk name bytes.  Tools that wish to enumerate
  ``all filters named X across a set of files'' have to either load
  the relevant plugin and compare to the numeric ID on disk, or
  accept that v2-written files will not match by name alone.

  \textbf{Scope of on-disk persistence: third-party filters only.}
  The pipeline-message name slot exists in \texttt{H5O\_PLINE\_VERSION\_2}
  only for filters with \texttt{id $\geq$ H5Z\_FILTER\_RESERVED} (i.e.,
  \texttt{id $\geq$ 256}, the third-party range).  For HDF~Group
  built-ins (\texttt{id < 256}: deflate, shuffle, fletcher32, szip,
  nbit, scale-offset), the V2 encoder and decoder
  (\texttt{H5O\_\_pline\_encode} / \texttt{H5O\_\_pline\_decode}) omit
  the name length field and name bytes entirely; no slot is reserved.
  Consequently \texttt{name} for built-ins has no version-2 slot on
  disk.  For the runtime API this is \emph{almost} always harmless: the
  registry supplies the name to \texttt{H5Pget\_filter2}, so the ``plugin
  unloaded, read name from disk'' fallback rarely engages for them.  The
  exception is that two built-ins are conditionally compiled ---
  \texttt{deflate} behind \texttt{H5\_HAVE\_FILTER\_DEFLATE} and
  \texttt{szip} behind \texttt{H5\_HAVE\_FILTER\_SZIP}
  (\texttt{H5Z\_\_init\_package}).  A build lacking either does not
  register it, so \texttt{H5Pget\_filter2} on such a build falls all the
  way through to the numeric ID formatted as a decimal string.  Only
  \texttt{shuffle}, \texttt{fletcher32}, \texttt{nbit}, and
  \texttt{scale-offset} are unconditionally present.

  \textbf{Version~3 does not close this gap, deliberately.}  An earlier
  draft of this RFC added an extension block carrying the canonical name
  for built-in entries, on the reasoning that a version-3 file storing
  \texttt{level~=~6} should say what it configures.  That was dropped
  after checking what actually consumes the name:

  \begin{itemize}
  \item \texttt{h5dump} never consults the registry or the on-disk slot
    for built-ins.  It switches on the filter ID and prints a hardcoded
    label, which is why it still reports \texttt{COMPRESSION DEFLATE} for
    a file whose deflate filter is unavailable.
  \item The six built-in IDs are permanently fixed and published in the
    file format specification.  Any reader that parses a pipeline message
    --- including one that never links libhdf5 --- can map ID to name
    from a six-entry table that cannot change.  Knowing the string
    \texttt{"deflate"} does not help it decompress anything; it needs the
    ID either way.
  \end{itemize}

  What remains is narrow: on a build compiled without deflate or szip,
  \texttt{H5Pget\_filter2} returns the numeric ID as a string for those
  two filters.  That is a pre-existing behaviour, affects a programmatic
  caller who already holds the ID, and does not justify a permanent
  format feature that could never later be removed.

  \textbf{Pre-existing \texttt{H5Pequal} behavior.}  The pipeline
  property's comparison callback (\texttt{H5P\_\_pline\_cmp}) does a
  \texttt{strcmp} of the name slot when comparing two pipelines.  This
  has been the case since the V2 pipeline-message format was
  introduced and is not changed by this RFC.  One observable
  consequence is that two pipelines with identical \texttt{id},
  \texttt{flags}, and \texttt{cd\_values} but different name slots
  (e.g., one read from disk carrying the plugin's canonical name, the
  other constructed in memory via \texttt{H5Pset\_filter} with
  \texttt{name = NULL}) compare as unequal under \texttt{H5Pequal}.
  This is not used inside libhdf5 for any correctness-relevant path;
  it surfaces only via the public \texttt{H5Pequal} API.  Code that
  needs to test pipeline equivalence at the I/O-behavior level should
  compare \texttt{id} and \texttt{cd\_values} directly via
  \texttt{H5Pget\_filter2}.

  \textbf{Length limit:} \texttt{name} must not exceed 255 bytes
  (excluding the NUL terminator).  \texttt{H5Zregister()} rejects a v3
  registration where \texttt{strlen(name) > 255} with
  \texttt{H5E\_BADVALUE}.  This bound is a sanity cap; the
  pipeline-message name field is variable-length and short names fit
  in the inline buffer (\texttt{H5Z\_COMMON\_NAME\_LEN}).

  A migration guide for plugin authors upgrading from v2 to v3 is
  produced alongside this RFC, covering at minimum: the strengthened
  contract on the \texttt{name} field (free-form debug comment in v2
  becomes the canonical name in v3), the version constant change, and
  the locations in the library where v2/v3 branching is required.

\item \texttt{description}---A human-readable, free-form summary of
  what the filter does, intended for users and tooling rather than
  programmatic lookup (e.g., \texttt{"Deflate (zlib) general-purpose
  lossless compression"}, \texttt{"SZIP lossless compression for
  scientific data"}).  Unlike \texttt{name}, the description is purely
  informational: it is \emph{not} persisted to disk, \emph{not} used
  for any identity comparison, and \emph{not} required to remain
  stable across plugin versions.  Plugin authors may set it to
  \texttt{NULL} if no useful description is available, in which case
  introspection tools fall back to displaying only the canonical
  name.  The field has no length limit beyond ordinary string
  conventions.  This is the v3 successor to the v1/v2 informal
  practice of writing a longer-form sentence into the \texttt{name}
  field; v3 separates the canonical identifier (\texttt{name}) from
  the prose (\texttt{description}) so that each can serve its purpose
  cleanly.
\end{itemize}

\verysubsection{Retrieval: \texttt{H5Zget\_filter\_class\_info}}
\label{sec:H5Zget-filter-info2}

The legacy \texttt{H5Zget\_filter\_info(filter, *flags)} returns only the
encode/decode configuration bits.  The v3 successor

\begin{minted}{c}
typedef struct H5Z_class_info_t {
    H5Z_filter_t  id;
    unsigned int  config_flags;
    const char   *name;
    const char   *description;
    bool          has_set_config;
    bool          has_get_config;
} H5Z_class_info_t;

herr_t H5Zget_filter_class_info(H5Z_filter_t filter,
                                H5Z_class_info_t *info);
\end{minted}

\noindent returns the same flag bits \emph{plus} the canonical \texttt{name},
the free-form \texttt{description}, and presence flags for the v3
\texttt{set\_config} / \texttt{get\_config} callbacks.  The function triggers
a dynamic plugin load if needed (same policy as \texttt{H5Zfilter\_avail});
unknown filter IDs return \texttt{H5E\_NOFILTER}.

String fields in \texttt{info} point into library-owned storage; their
lifetime extends until the filter is unregistered.  Callers must not
free them.

This is the supported way to read a filter's \texttt{description}, since
that field is not persisted to disk and only exists when the plugin is
loaded.  Per-instance parameter strings (reflecting actual \texttt{cd\_values}
stored in a dataset's pipeline) are obtained via
\texttt{H5Pget\_filter\_params\_by\_idx}.  The original
\texttt{H5Zget\_filter\_info(filter, *flags)} remains available for callers
that only need the encode/decode bits.

\subsection{Identity Allocation and Uniqueness}
\label{sec:identity-allocation}

The numeric \texttt{id} and the canonical name carried in \texttt{name}
together form a filter's public identity.  Allocation is coordinated administratively
by the HDF Group, and conflicts are caught at runtime by
\texttt{H5Zregister()}.

\textbf{Current state of the registry (informational).}  Today the
list of allocated third-party filter IDs lives on the HDF Group
portal as a web page (``Registered Filter Plugins''), not as a
versioned artifact in the HDF5 source tree.  This RFC does \emph{not}
change that arrangement, but the limitation is real: the page is not
tagged with library releases and tools cannot consume it without
scraping.  Moving the registry into the HDF5 source tree (so that the
source is the single source of truth and the web view is generated
from it) is tracked separately as HDF5 issue
\href{https://github.com/HDFGroup/hdf5/issues/6407}{\#6407} and is
out of scope for this RFC.  The runtime checks below apply regardless of where the
registry physically lives.

\verysubsection{What \texttt{H5Zregister} checks today (numeric \texttt{id})}

\begin{itemize}
\item \textbf{Range check.}  The numeric \texttt{id} must lie in
  the range \texttt{[H5Z\_FILTER\_RESERVED, H5Z\_FILTER\_MAX]} =
  \texttt{[256, 65535]}.  IDs 0--255 are reserved for HDF~Group built-ins
  (\texttt{H5Z\_FILTER\_DEFLATE}=1, \texttt{\_SHUFFLE}=2,
  \texttt{\_FLETCHER32}=3, \texttt{\_SZIP}=4, \texttt{\_NBIT}=5,
  \texttt{\_SCALEOFFSET}=6); values above $65535$ do not fit the
  16-bit on-disk filter slot in \texttt{H5O\_PLINE}.
\item \textbf{Duplicate check.}  If another class with the same
  \texttt{id} is already in the in-process filter registry, the second
  registration is rejected.  First-registered wins.
\item \textbf{No semantic check.}  The library does \emph{not} consult
  any external list to verify that, e.g., ID 32013 was actually
  allocated by the registry to ZFP.  A plugin can hard-code any ID in
  the legal range; the runtime can only tell that the ID is
  syntactically valid and not already taken in this process.
\end{itemize}

\verysubsection{Extending the same model to the canonical name}

The canonical name carried in \texttt{name} is governed by an
identical three-layer model:

\begin{itemize}
\item \textbf{Administrative allocation.}  The HDF Group's filter
  registration process assigns the canonical name alongside the
  numeric \texttt{id}.  A plugin author requesting ID 32013 also
  receives, in the same registration, the canonical name string
  (e.g., \texttt{"zfp"}).  This RFC adds the canonical name to the
  information the registration records; where that record physically
  lives (web page today, source-tree file in the future) is orthogonal
  to the runtime semantics specified here.
\item \textbf{Syntactic check at \texttt{H5Zregister}.}  For v3
  plugins, \texttt{name} must be a non-NULL, non-empty string of at
  most 255 bytes (already specified in the field description above)
  drawn from the character class \texttt{[A-Za-z0-9\_.-]}.  Names are
  matched case-sensitively.  Registrations that violate the syntax are
  rejected with \texttt{H5E\_BADVALUE}.
\item \textbf{In-process duplicate check at \texttt{H5Zregister}.}  If
  the in-process registry already contains a v3 filter with the same
  \texttt{name} but a different \texttt{id} (or vice versa), the
  second registration is rejected with \texttt{H5E\_CANTREGISTER}.  As
  with numeric IDs, first-registered wins.
\item \textbf{No semantic check.}  The library does \emph{not} verify
  that the (name, id) pair carried by a plugin matches the public
  registry.  A rogue plugin can declare any well-formed name in its
  source.  Coordinated allocation through the registry is the only
  guarantee that \texttt{"zfp"} means the same thing on every system,
  exactly as it is the only guarantee today that ID 32013 does.
\end{itemize}

\verysubsection{What this does and does not prevent}

The in-process duplicate check is sufficient to keep a single HDF5
process internally consistent: two plugins claiming the same name or
ID cannot both be active in the same library load.  It does \emph{not}
prevent two independently-built plugins from declaring the same
\texttt{name} value in their source.  The collision surfaces only
when a user attempts to load both into one process---at which point
the second registration fails and the user must remove or rebuild one
of the plugins.  This mirrors today's behaviour for duplicate numeric
IDs and is, in practice, why the registry exists.

Recommended convention (non-normative): third-party plugins that have
not gone through HDF Group filter registration should self-namespace
their canonical names (e.g., \texttt{"org.example.fastlz"}) to make
accidental collisions vanishingly unlikely.  Coordinated registration
remains the recommended path for plugins that want a short, bare name.

\subsection{Callback Specifications}
\label{sec:callback-specs}

\verysubsection{\texttt{H5Z\_func2\_t} --- Extended filter callback}

\texttt{H5Z\_class3\_t} uses \texttt{H5Z\_func2\_t} rather than the
existing \texttt{H5Z\_func\_t}.  \texttt{H5Z\_class2\_t} filters are
unaffected.

\begin{itemize}
\item \texttt{flags}, \texttt{cd\_nelmts}, \texttt{cd\_values},
  \texttt{nbytes}, \texttt{buf\_size}, \texttt{buf}---Same semantics as
  \texttt{H5Z\_func\_t}.

\item \texttt{dxpl\_id}---The active data-transfer property list for the
  current \texttt{H5Dread} or \texttt{H5Dwrite} call.  Filters that need
  non-serializable runtime handles (e.g., \texttt{MPI\_Comm},
  \texttt{cudaStream\_t}, per-read quality parameters) obtain them by
  calling \texttt{H5Pget()} on this DXPL.  The caller registers a custom
  property on the DXPL with \texttt{H5Pinsert2} or \texttt{H5Pregister2}
  and sets it before each I/O call.  Filters that do not use the DXPL may
  ignore this parameter.

\item \texttt{scaled}---Array of \texttt{ndims} scaled chunk coordinates
  (chunk offset in chunk units, not element units).  This is the same
  \texttt{scaled[]} array present at every internal pipeline call site.
  Filters performing spatially-aware compression (e.g., ROIBIN-SZ spatial
  masks, GPU tile routing) use these coordinates to determine which region
  of the dataset they are operating on.  Filters that do not need spatial
  information may ignore this parameter.

\item \texttt{ndims}---Number of elements in \texttt{scaled[]};
  equals the dataset's chunk rank.
\end{itemize}

\noindent Passing the DXPL and chunk coordinates as parameters to the
existing callback rather than via a separate callback or a new public
accessor function avoids call-ordering hazards under multithreading
and does not require a new public API function.

\verysubsection{\texttt{H5Z\_set\_config\_func\_t}}

\begin{itemize}
\item \texttt{params}---The key-value parameter string (e.g.,
  \texttt{"mode=\textquotedbl{}rate\textquotedbl{}, rate=3.5"}). \texttt{NULL} if no parameters were provided.
\item \texttt{flags}---On input, contains the flags value from the API call. The
  callback can modify this value; the modified value is what
  \texttt{H5Pappend\_filter} writes into the DCPL. This gives the filter the
  final say on properties like \texttt{H5Z\_FLAG\_MANDATORY} vs.\
  \texttt{H5Z\_FLAG\_OPTIONAL}. Callers that need to detect a flag override can
  compare the value they passed with the flags returned by
  \texttt{H5Pget\_filter2} after the call.
\item \texttt{cd\_nelmts}---On input, points to a value of~0. On output, set to the
  number of elements written to \texttt{cd\_values} (or the number of elements
  required, if \texttt{cd\_values} is \texttt{NULL}).
\item \texttt{cd\_values}---On output, populated with the filter's client data. If
  \texttt{NULL}, the callback still sets \texttt{cd\_nelmts} to the required count,
  enabling a two-pass size query pattern. The library calls the callback once
  with \texttt{cd\_values=NULL} to determine the required size, allocates
  accordingly, and calls it again with a sufficiently sized array.

  \textbf{Two-pass identity contract:} The callback returns the same
  \texttt{cd\_nelmts} value on both invocations. If the second-pass \texttt{cd\_nelmts}
  differs from the first-pass value in either direction, the library
  returns an error. A smaller second-pass value would silently truncate the
  populated array; a larger value would constitute a buffer overflow. Both
  represent a buggy callback. Document this contract in
  \texttt{H5Zdevelop.h} as part of the \texttt{H5Z\_set\_config\_func\_t} specification.

  Additionally, the library validates on the second pass that
  \texttt{cd\_nelmts} does not exceed the allocated capacity; if it does, the
  library returns an error rather than writing out of bounds.

  The library also verifies that \texttt{cd\_nelmts} does not exceed
  \texttt{UINT16\_MAX}, the current file-format limit on the number of
  \texttt{cd\_values} elements per filter entry.  A callback returning a count
  larger than this is rejected with \texttt{H5E\_BADVALUE}.  The parameter
  type is \texttt{size\_t} rather than a narrower type so that the limit can be
  raised in a future format revision without changing the callback signature.
  Note: the per-string token count is separately bounded by
  \texttt{H5Z\_CONFIG\_MAX\_PARAMS} (64), a parser-level limit applied before
  \texttt{set\_config} is ever invoked (\SectionRef{sec:param-overview}).
\item \texttt{cd\_values\_size}---The capacity of the \texttt{cd\_values} array in
  bytes (0 when \texttt{cd\_values} is \texttt{NULL}).
\item Returns non-negative on success, negative on failure.
\end{itemize}

The callback should use \texttt{H5Epush} to report meaningful error messages for
invalid parameters.

\verysubsection{Unknown-key handling}
A \texttt{set\_config} callback should reject unrecognized keys by returning a
negative value and pushing \texttt{H5E\_BADVALUE} with a message identifying the
key.  This is the primary defense against misspelled parameter names (e.g.,
\texttt{"clevl=6"} instead of \texttt{"clevel=6"}), which would otherwise be
silently ignored.  Because the string API does not have the compile-time safety
of named constants, rejecting unknown keys is strongly recommended for
usability.

However, a filter can choose to silently ignore unrecognized keys to support
forward compatibility: a caller that targets a newer version of a plugin can
write a parameter string containing new keys and have it accepted by an older
version of the same plugin without error, falling back to defaults for the
unknown parameters.  Filter authors who choose this approach should document it
clearly so that callers are not misled into believing all keys were acted upon.

All built-in filter \texttt{set\_config} callbacks reject unknown keys.  Document
this guidance in \texttt{H5Zdevelop.h} as part of the
\texttt{H5Z\_set\_config\_func\_t} contract.

\verysubsection{Locale requirement for \texttt{set\_config}}
\texttt{set\_config} callbacks that parse numeric values from the parameter
string (e.g., converting a rate or tolerance to \texttt{double}) use
C-locale numeric conversion. Process-wide locale settings (e.g., a
comma-decimal locale) do not affect parameter interpretation. In practice,
this means using \texttt{strtod} under \texttt{uselocale(newlocale(LC\_NUMERIC\_MASK,
"C", 0))} or a locale-independent equivalent. The library-provided
\texttt{H5Zconfig\_get\_str} (\SectionRef{sec:config-get-param}) returns raw
string values; it is the callback's responsibility to convert them to numeric
types in a locale-safe manner.  The numeric accessors
(\texttt{H5Zconfig\_get\_int}, \texttt{H5Zconfig\_get\_double}) perform the
conversion inside the library and are locale-safe already. This requirement mirrors the output-side locale
requirement on \texttt{get\_config} (\SectionRef{sec:callback-specs}) and ensures
round-trip correctness. Document this requirement in
\texttt{H5Zdevelop.h} as part of the \texttt{H5Z\_set\_config\_func\_t} specification.

\verysubsection{\texttt{H5Z\_get\_config\_func\_t}}

\begin{itemize}
\item Provides a best-effort human-readable representation of the filter
  configuration encoded in \texttt{cd\_values}.  With the parameter string
  persisted on disk (\SectionRef{sec:pline-v3}), this callback is a
  \emph{fallback}: the library invokes it only for pipeline entries that
  carry no stored string (raw \texttt{cd\_values} configuration, pre-RFC
  files, or libver-forced version-2 messages), and for the runtime
  ``effective configuration'' view of what the filter actually applied.
  Due to the lossy nature of the
  \texttt{cd\_values} encoding (e.g., floating-point values quantised to integers,
  information collapsed during the \texttt{set\_config} conversion), the output
  cannot in general be guaranteed to round-trip back to an identical
  configuration.  See the note on reconstructed strings in
  \SectionRef{sec:introspection}.
\item Follows the standard HDF5 buffer-size query pattern: \texttt{buf\_size} is
  an in/out parameter. On entry, \texttt{*buf\_size} is the total capacity of
  \texttt{buf} in bytes, \textbf{including} the slot for the NUL terminator
  (i.e., \texttt{*buf\_size~$\geq$~strlen(output)~+~1}); on return,
  \texttt{*buf\_size} is set to the number of characters written, excluding the
  NUL terminator.  This matches the convention used by \texttt{snprintf} and all
  other standard C buffer-size arguments, so implementations may write directly
  with \texttt{snprintf(buf,~*buf\_size,~...)} without adjustment.  If
  \texttt{buf} is \texttt{NULL}, the callback still sets \texttt{*buf\_size} to
  the required character count (excluding NUL) and returns success, enabling a
  size query.  \texttt{H5Pget\_filter\_params\_by\_idx} allocates
  \texttt{needed~+~1} bytes for its internal buffer and passes
  \texttt{*buf\_size~=~needed~+~1} on the populate call, where \texttt{needed}
  is the character count returned by the preceding size-query call.
\item Returns \texttt{herr\_t}: zero on success, negative on failure.
\item The output conforms to the grammar defined in
  \SectionRef{sec:param-overview} so that it is at least valid input to
  \texttt{set\_config}, even if the resulting configuration may differ from the
  original due to precision loss or encoding limitations.
\item \textbf{Locale and precision requirement:} \texttt{get\_config}
  implementations that format floating-point values must use
  \texttt{\%.17e} (e.g., \texttt{snprintf(buf, n, "\%.17e", val)}).
  This format always contains a decimal point and exponent (valid TOML\,v1.0
  float) and guarantees exact IEEE\,754 \texttt{double} round-trips via 17
  significant digits (\texttt{DBL\_DECIMAL\_DIG}).  Do not use \texttt{\%a}
  (hex-float, not valid TOML), \texttt{\%g} (may omit decimal point, producing
  a TOML integer), \texttt{\%f}, or fewer than 17 significant digits.
  \textbf{Locale caveat:} \texttt{snprintf} respects \texttt{LC\_NUMERIC}; in
  locales with a comma decimal separator the output is not valid TOML.
  Implementations must replace any comma in the formatted number with a
  period before returning the string.
  See \SectionRef{sec:float-precision} for full rationale.
  Document this requirement in \texttt{H5Zdevelop.h} as part of the
  \texttt{H5Z\_get\_config\_func\_t} specification.
\end{itemize}


\subsection{Future: Name-Based Filter ID Lookup}
\label{sec:future-name-lookup}

\begin{outofscope}
Name-based filter ID lookup is out of scope for this RFC.  This
subsection records the design intent so that the canonical-name
contract on \texttt{H5Z\_class3\_t.name} defined here is
forward-compatible with the planned mechanism; no new public API is
added by this RFC.
\end{outofscope}

A follow-on change will let callers resolve a filter's numeric
\texttt{H5Z\_filter\_t} \texttt{id} from its canonical name, without
requiring the plugin to be pre-loaded by ID.  Three design constraints
shape the approach:

\begin{itemize}
\item \textbf{No static library-internal name table.}  Embedding a
  hard-coded name$\rightarrow$ID map in the HDF5 library has been
  rejected: such tables go stale (the ZFP project rename is a real
  example), and place the maintenance burden on the library for changes
  to plugins it does not own.

\item \textbf{Plugins own their own identity.}  Each v3 plugin
  advertises its canonical name in the \texttt{name} field of its
  \texttt{H5Z\_class3\_t} struct; the plugin loader can read this
  string after \texttt{dlopen}.  The library does not need a registry
  to know what a plugin calls itself.
\end{itemize}

The planned mechanism is therefore \emph{full plugin discovery}: the
plugin loader's key type (\texttt{H5PL\_key\_t}) is extended with a
name-based filter branch.  To locate the plugin, the loader first
probes for libraries that match a standard naming convention---e.g.,
\texttt{libh5filter\_<name>.so}---and only falls back to a full scan
of the plugin directories if no matching file is found.  Once the file
is opened, the v3 plugin's \texttt{H5Z\_class3\_t} struct supplies
both the \texttt{name} (to confirm the match) and the numeric
\texttt{id} required by the DCPL.  This approach handles plugin
renames without library updates, works for plugins never previously
loaded, and does not depend on file-format encoding.  v2 plugins
(whose \texttt{name} field carries an unstructured debug comment
rather than a canonical identifier) do not participate in name-based
lookup.

\textbf{HPC note.}  The naming-convention fast path is a normative
requirement, not a hint: in a parallel job with thousands of MPI ranks
on a shared file system (Lustre, GPFS), a brute-force
\texttt{dlopen()} of every shared library in the plugin directory on
each rank would generate a metadata storm capable of stalling the
file system's metadata server.  The fast path keeps a missed lookup
to a single \texttt{stat()} per rank.  The directory-wide fallback
scan is retained only for hand-installed plugins that do not follow
the convention; deployments concerned with HPC scaling should
require the convention.

\textbf{Optional filters and the missing-ID constraint.}  The current
\texttt{H5O\_PLINE} on-disk format strictly requires a numeric
\texttt{H5Z\_filter\_t} for every pipeline entry.  Name-based
configuration therefore requires the plugin to be present at
configuration time so the numeric \texttt{id} can be resolved before
the entry is appended to the DCPL.  If a caller requests an optional
filter by name and the plugin cannot be found, the API must return a
hard error: the library has no legal way to record a ``missing''
pipeline entry without an \texttt{id}, and silently dropping the
entry would alter the user's intended data schema without leaving a
trace in the file.  This differs from the existing
\texttt{H5Z\_FLAG\_OPTIONAL} semantics for ID-based configuration,
where the \texttt{id} is known at \texttt{H5Pset\_filter} time and
only the plugin body is missing at I/O time---those semantics remain
unchanged for ID-based callers.

True soft-failure semantics for missing name-based filters require a
format extension capable of storing name-only pipeline entries that
carry a canonical name without a resolved numeric \texttt{id}.  The
version-3 pipeline message defined by this RFC
(\SectionRef{sec:pline-v3}) does not define such entries --- every entry
it writes still carries a numeric \texttt{id} --- but it does define the
framing they need.  A name-only entry is a critical extension block: an
entry whose identity lives in the block rather than in the
\texttt{filter\_id} field cannot be interpreted by a reader that ignores
the block, which is exactly what the critical bit expresses
(\SectionRef{sec:pline-v3-layout}).  When that mechanism is specified,
it therefore arrives as a new block type within version~3 --- readable
by libraries that shipped this RFC, which will reject precisely the
name-only entries and nothing else --- rather than as a version~4 that
those libraries could not open at all.
Such entries would be resolved at open time on systems where the
plugin is installed and gracefully skipped where it is not.  Until
that format is available, callers that need optional name-based
filters must check for plugin presence themselves and adjust the
pipeline accordingly.  No new flag analogous to
\texttt{H5Z\_FLAG\_OPTIONAL} is introduced; when the future API
appears, callers will pass \texttt{H5Z\_FLAG\_OPTIONAL} through the
existing \texttt{flags} bitmask, and its meaning will be defined by
the new on-disk encoding.

\subsection{Backward Compatibility}

\texttt{H5Zregister()} inspects the \texttt{version} field to determine whether the
structure is \texttt{H5Z\_class1\_t} (legacy), \texttt{H5Z\_class2\_t}, or
\texttt{H5Z\_class3\_t}. Existing v1 and v2 plugins continue to function without
modification. The new callbacks are never accessed for v1/v2 registrations.
\texttt{H5Z\_class3\_t} is a new type, not a modification of \texttt{H5Z\_class2\_t}.

A v3 plugin remains fully usable through the traditional \texttt{H5Pset\_filter} API.
Upgrading to v3 is optional and additive.

Files written by a v3-aware library carry the v3 plugin's canonical
name (its \texttt{name} field) in the filter-pipeline message's name
slot -- the same on-disk slot existing v2 plugins have always used.
No extra \texttt{cd\_values} slots are appended, so \texttt{cd\_nelmts}
as seen by the plugin's execution callback is exactly what
\texttt{set\_config} (or the caller of \texttt{H5Pset\_filter})
produced, regardless of the pipeline-message version.

Readability by older HDF5 \emph{libraries} is governed by the
pipeline-message version (\SectionRef{sec:pline-v3-gating}): pipelines
configured without parameter strings are written as version-2 messages,
byte-identical to pre-RFC output and readable everywhere.  Pipelines that
carry stored configuration strings are written as version-3 messages,
which pre-RFC libraries reject at dataset-open time; callers who need
old-reader compatibility bound the file format with
\texttt{H5Pset\_libver\_bounds}, which drops the stored strings and
reverts to version-2 output (\SectionRef{sec:pline-v3-gating}).

When \texttt{H5Pget\_filter2} is called for a v3 filter, it returns
the canonical name (\texttt{name}) from the runtime registry if the
plugin is loaded, falls back to the name stored in the pipeline
message at filter-add time, and finally falls back to the numeric
filter ID formatted as a decimal string.

\section{Public API}
\label{sec:public-api}

\subsection{Single-Filter Configuration}
\label{sec:append-filter}

\verysubsection{Parameter type}

\begin{minted}{c}
typedef enum {
    H5Z_PARAMS_CDVALUES = 0,  /* raw cd_values array (same as H5Pset_filter) */
    H5Z_PARAMS_STRING   = 1,  /* human-readable key=value string              */
} H5Z_params_type_t;

typedef struct {
    H5Z_params_type_t type;
    union {
        struct {
            size_t          cd_nelmts;
            const unsigned *cd_values;
        } raw;
        const char *str;
    } u;
} H5Z_params_t;
\end{minted}

Convenience initialiser macros are provided for the two common cases:

\begin{minted}{c}
/* C99: compound literals with designated initialisers */
#define H5Z_PARAMS_RAW(n, vals) \
    ((H5Z_params_t){ H5Z_PARAMS_CDVALUES, { .raw = { (n), (vals) } } })
#define H5Z_PARAMS_STR(s) \
    ((H5Z_params_t){ H5Z_PARAMS_STRING,   { .str  = (s)            } })
\end{minted}

\verysubsection{Compound literal lifetime}
Both macros expand to C99 compound literals.  A compound literal has
automatic storage duration within its enclosing block---it is not a
temporary that expires at the semicolon.  Passing \texttt{\&H5Z\_PARAMS\_STR("level=6")}
to \texttt{H5Pappend\_filter} is therefore valid C99: the literal's
address is well-defined for the duration of the call.  However, storing
that address in a pointer that outlives the enclosing block is undefined
behaviour; callers who need to store an \texttt{H5Z\_params\_t} beyond a
single call should declare a named variable instead:

\begin{minted}{c}
/* Safe: compound literal address taken for the duration of one call */
H5Pappend_filter(plist, H5Z_FILTER_DEFLATE,
                     H5Z_FLAG_MANDATORY, &H5Z_PARAMS_STR("level = 6"));

/* Also safe: named variable with explicit lifetime */
H5Z_params_t p = H5Z_PARAMS_STR("level = 6");
H5Pappend_filter(plist, H5Z_FILTER_DEFLATE, H5Z_FLAG_MANDATORY, &p);
\end{minted}

\verysubsection{Function signature}

\begin{minted}{c}
herr_t H5Pappend_filter(
    hid_t              plist_id,
    H5Z_filter_t       id,
    unsigned           flags,
    const H5Z_params_t *params
);
\end{minted}

\verysubsection{Description}
Configures the filter identified by \texttt{id} and appends it to the
existing filter pipeline on \texttt{plist\_id}.  The pipeline is subject to
the existing maximum of \texttt{H5Z\_MAX\_NFILTERS} (32) entries.

\texttt{H5Pappend\_filter} accepts either a raw \texttt{cd\_values} array
(\texttt{H5Z\_PARAMS\_CDVALUES}) or a key=value parameter string
(\texttt{H5Z\_PARAMS\_STRING}) through the tagged union \texttt{H5Z\_params\_t}.
Passing \texttt{NULL} for \texttt{params} is equivalent to
\texttt{H5Z\_PARAMS\_CDVALUES} with \texttt{cd\_nelmts = 0} and is valid for
filters that take no parameters.

The name \texttt{H5Pappend\_filter} reflects its semantics: each call appends
a new entry to the filter pipeline.  Changing the parameters of an entry that
is already present is handled by \texttt{H5Pmodify\_filter\_by\_idx}
(\SectionRef{sec:modify-filter}), which accepts the same
\texttt{H5Z\_params\_t} and preserves the entry's position.

When \texttt{type} is \texttt{H5Z\_PARAMS\_CDVALUES}, the function behaves
identically to \texttt{H5Pset\_filter}: the \texttt{cd\_values} array is stored
in the DCPL without invoking any plugin callback.

When \texttt{type} is \texttt{H5Z\_PARAMS\_STRING}, the library locates or
loads the filter plugin, invokes the filter's \texttt{set\_config} callback to
translate the parameter string into \texttt{cd\_values}, and stores the result.
In addition, the validated parameter string is retained, in canonical form, in the DCPL
pipeline entry and persisted to the file in the version-3 pipeline message
(\SectionRef{sec:pline-v3}), making the configuration introspectable without
the plugin and round-trippable without loss.

\textbf{Empty-string handling:} If \texttt{u.str} is \texttt{NULL} or the empty
string \texttt{""}, \texttt{H5Pappend\_filter} treats the call as ``no
parameters''. The library locates the filter plugin and inspects its class
record:
\begin{itemize}
\item If the plugin does \emph{not} implement \texttt{set\_config} (the
  typical case for parameterless built-ins such as shuffle, fletcher32, and
  nbit), the library appends the filter with \texttt{cd\_nelmts~=~0} and no
  callback is invoked. Such filters are usable through the
  \texttt{H5Z\_PARAMS\_STRING} form without being forced to provide a
  \texttt{set\_config} callback that has nothing to do.
\item If the plugin \emph{does} implement \texttt{set\_config}, the callback
  is invoked with \texttt{params~=~NULL}. The plugin decides whether an
  empty configuration is acceptable: parameterless or fully-defaulted
  filters may return success with the appropriate \texttt{cd\_values}, while
  filters that strictly require parameters (e.g., Scale-Offset, SZIP) may
  return \texttt{H5E\_BADVALUE} so the failure surfaces at
  \texttt{H5Pappend\_filter} rather than later at \texttt{H5Dcreate} or
  I/O time. This preserves the fail-fast contract documented below.
\end{itemize}

\verysubsection{Eager plugin loading}
\textbf{Note:} Unlike \texttt{H5Pset\_filter}, which stores raw \texttt{cd\_values}
without consulting the plugin, \texttt{H5Pappend\_filter} with
\texttt{H5Z\_PARAMS\_STRING} loads the filter plugin and invokes its
\texttt{set\_config} callback at call time. The plugin must therefore be
available when \texttt{H5Pappend\_filter} is called, not merely when
\texttt{H5Dcreate} runs. If the plugin cannot be found,
\texttt{H5Pappend\_filter} returns \texttt{H5E\_NOFILTER} immediately rather
than deferring the failure to \texttt{H5Dcreate}. This is a deliberate
design choice---fail-fast at configuration time gives clearer errors than
deferred failure during dataset creation---but it differs from the lazy
behavior of \texttt{H5Pset\_filter} and may surprise callers porting
existing code.

\verysubsection{Behavioral note on flags}
The caller controls flags directly.  When \texttt{type} is
\texttt{H5Z\_PARAMS\_STRING}, the flags value is passed through the filter's
\texttt{set\_config} callback, which may modify it (e.g., SZIP unconditionally
forces \texttt{H5Z\_FLAG\_OPTIONAL}).  Callers that need to detect a flag
override can compare the value they passed with the flags returned by
\texttt{H5Pget\_filter2} after the call.  See \SectionRef{sec:callback-specs}.

\verysubsection{Parameters}

\begin{itemize}
\item \texttt{plist\_id}---A dataset creation property list identifier.
\item \texttt{id}---The filter identifier (\texttt{H5Z\_filter\_t}).  For
  built-in filters, use the predefined constants
  (\texttt{H5Z\_FILTER\_DEFLATE}, etc.).  For externally registered filters,
  use the numeric ID assigned by the HDF Group filter registry.
\item \texttt{flags}---A bit mask specifying filter behavior
  (\texttt{H5Z\_FLAG\_MANDATORY}, \texttt{H5Z\_FLAG\_OPTIONAL}).
\item \texttt{params}---A pointer to an \texttt{H5Z\_params\_t} describing the
  filter configuration, or \texttt{NULL} for filters that take no parameters.
  \begin{itemize}
  \item \texttt{H5Z\_PARAMS\_CDVALUES}: \texttt{u.raw.cd\_nelmts} and
    \texttt{u.raw.cd\_values} are used directly, identical to
    \texttt{H5Pset\_filter}.
  \item \texttt{H5Z\_PARAMS\_STRING}: \texttt{u.str} is a comma-separated
    key=value parameter string.  \texttt{NULL} or an empty string means ``no
    parameters'' and is valid for parameterless filters (shuffle, fletcher32,
    nbit).
  \end{itemize}
\end{itemize}

\verysubsection{Returns}
Non-negative on success; negative on failure.

\verysubsection{Errors}

\begin{itemize}
\item \texttt{H5E\_NOFILTER}---(\texttt{H5Z\_PARAMS\_STRING} only) The filter
  plugin could not be found or loaded.
\item \texttt{H5E\_UNSUPPORTED}---(\texttt{H5Z\_PARAMS\_STRING} only) The
  filter was found but does not implement \texttt{set\_config}, and a
  non-empty parameter string was supplied.  An empty string or
  \texttt{NULL} is accepted when \texttt{set\_config} is absent; when
  \texttt{set\_config} is present, an empty/NULL string is forwarded to
  the callback for validation (see Empty-string handling in the
  Description).
\item \texttt{H5E\_BADVALUE}---The parameter string is malformed, the
  \texttt{params} type field is unrecognised, or \texttt{set\_config} rejected
  the parameter string.
\item \texttt{H5E\_CANTINIT}---The \texttt{set\_config} callback returned a
  \texttt{cd\_nelmts} value exceeding \texttt{UINT16\_MAX} or the library's
  internal filter-table limit.
\end{itemize}

\verysubsection{Usage examples}

\begin{minted}{c}
/* --- String form (TOML inline table content) --- */

/* Built-in deflate: integer value */
H5Pappend_filter(plist, H5Z_FILTER_DEFLATE, H5Z_FLAG_MANDATORY,
                     &H5Z_PARAMS_STR("level = 6"));

/* External plugin (ZFP): string + float values */
H5Pappend_filter(plist, H5Z_FILTER_ZFP, H5Z_FLAG_MANDATORY,
                     &H5Z_PARAMS_STR("mode = \"rate\", rate = 3.5"));

/* Boolean flag */
H5Pappend_filter(plist, H5Z_FILTER_BLOSC, H5Z_FLAG_MANDATORY,
                     &H5Z_PARAMS_STR("fast_mode = true, level = 6"));

/* Parameterless filter */
H5Pappend_filter(plist, H5Z_FILTER_SHUFFLE, H5Z_FLAG_MANDATORY, NULL);

/* --- Raw cd_values form (equivalent to H5Pset_filter) --- */

unsigned level = 6;
H5Pappend_filter(plist, H5Z_FILTER_DEFLATE, H5Z_FLAG_MANDATORY,
                     &H5Z_PARAMS_RAW(1, &level));

/* --- Building a mixed pipeline --- */
H5Pappend_filter(plist, H5Z_FILTER_SHUFFLE,    H5Z_FLAG_MANDATORY, NULL);
H5Pappend_filter(plist, H5Z_FILTER_DEFLATE,    H5Z_FLAG_MANDATORY,
                     &H5Z_PARAMS_STR("level = 9"));
H5Pappend_filter(plist, H5Z_FILTER_FLETCHER32, H5Z_FLAG_MANDATORY, NULL);
\end{minted}


\subsection{Modifying an Existing Entry}
\label{sec:modify-filter}

\begin{minted}{c}
herr_t H5Pmodify_filter_by_idx(
    hid_t                plist_id,
    unsigned             filter_idx,
    unsigned             flags,
    const H5Z_params_t  *params
);
\end{minted}

\verysubsection{Description}
Replaces the configuration of the filter already at position
\texttt{filter\_idx} in \texttt{plist\_id}'s pipeline, leaving its position
and filter ID unchanged.  \texttt{params} is interpreted exactly as
\texttt{H5Pappend\_filter} interprets it (\SectionRef{sec:append-filter}):

\begin{itemize}
\item \texttt{H5Z\_PARAMS\_STRING}: the string is validated and resolved
  through the filter's \texttt{set\_config} callback --- the same two-pass
  protocol \texttt{H5Pappend\_filter} uses --- and both the resulting
  \texttt{cd\_values} and the verbatim string replace the entry's current
  ones.  The entry keeps a stored configuration string.
\item \texttt{H5Z\_PARAMS\_CDVALUES}: the \texttt{cd\_values} array
  replaces the entry's current one and any stored string is cleared,
  matching \texttt{H5Pmodify\_filter} exactly
  (\SectionRef{sec:dcpl-retention}).
\end{itemize}

\verysubsection{Why this function exists}

Without it, the only way to change a filter's parameters is
\texttt{H5Pmodify\_filter}, which takes raw \texttt{cd\_values} and
therefore clears the stored string.  That makes the documented editing
pattern --- read \texttt{cd\_values}, mutate, write back --- silently
downgrade an entry from an exact, plugin-free configuration string to
\texttt{get\_config} reconstruction, with no error and no diagnostic.  The
loss is invisible until someone inspects the file on a machine without the
plugin installed and finds a dataset that reports less than its siblings.

The asymmetry is the problem.  Expressing a configuration as
\texttt{"level = 6"} at append time produces a self-describing entry;
expressing the same intent as an edit produces one that is not, and no API
short of \texttt{H5Premove\_filter} plus a fresh \texttt{H5Pappend\_filter}
restores it.  Remove-and-re-append is not an acceptable substitute: it
moves the entry to the end of the pipeline, silently changing filter order
and, for order-sensitive pipelines such as shuffle-then-deflate, the
compressed result.  A caller should not have to choose between preserving
introspectability and preserving pipeline order.

\verysubsection{Why by index, not by filter ID}

\texttt{H5Pmodify\_filter} addresses entries by filter ID and resolves to
the \emph{first} matching entry.  HDF5 pipelines legally contain the same
filter ID more than once (\SectionRef{sec:append-filter}), so an
ID-addressed modify silently edits the wrong entry in exactly those
pipelines.  This function indexes instead, which removes the ambiguity and
matches \texttt{H5Pget\_filter\_params\_by\_idx}
(\SectionRef{sec:introspection}): the index a caller reads a configuration
with is the index it writes one back with.

\verysubsection{Parameters}
\begin{itemize}
\item \texttt{plist\_id} --- Dataset or group creation property list.
\item \texttt{filter\_idx} --- Zero-based position in the pipeline, in the
  same numbering \texttt{H5Pget\_filter2} and
  \texttt{H5Pget\_filter\_params\_by\_idx} use.
\item \texttt{flags} --- Replaces the entry's flags, subject to the same
  \texttt{set\_config} adjustment rules as \texttt{H5Pappend\_filter}
  (\SectionRef{sec:set-config-template}); passing the value previously
  returned by \texttt{H5Pget\_filter2} leaves them effectively unchanged.
\item \texttt{params} --- New configuration, or \texttt{NULL} for a
  parameterless filter.
\end{itemize}

\verysubsection{Returns and errors}
Returns a non-negative value on success, negative on failure.  It is an
error if \texttt{filter\_idx} is out of range, if \texttt{params} uses
\texttt{H5Z\_PARAMS\_STRING} for a filter whose registered class does not
implement \texttt{set\_config}, or if \texttt{set\_config} rejects the
string.  On any failure the entry is left exactly as it was: the new
\texttt{cd\_values} and string are staged and swapped in only after
\texttt{set\_config} succeeds, so a rejected edit cannot leave an entry
holding a string that disagrees with its \texttt{cd\_values}.

\verysubsection{Relationship to \texttt{H5Pmodify\_filter}}
\texttt{H5Pmodify\_filter} is unchanged and undeprecated.  Existing callers
keep working, including the read-mutate-write pattern; the only difference
is that its string-clearing behaviour is now a documented consequence with
a documented alternative rather than the only available path.

\subsection{Pipeline Introspection}
\label{sec:introspection}

\begin{minted}{c}
herr_t H5Pget_filter_params_by_idx(
    hid_t     plist_id,
    unsigned  filter_idx,
    char     *params_buf,
    size_t    params_buf_size,
    size_t   *params_len
);
\end{minted}

\verysubsection{Description}
Returns the human-readable parameter string for the filter at position
\texttt{filter\_idx} in the pipeline.  Three sources are consulted in
order of decreasing fidelity:

\begin{enumerate}
\item \textbf{The stored configuration string.}  If the entry carries a
  persisted parameter string (\SectionRef{sec:config-storage-rules}) ---
  retained in the DCPL at \texttt{H5Pappend\_filter} time, or decoded from
  a version-3 pipeline message --- that string is returned verbatim.  This
  is exact and requires no plugin.
\item \textbf{\texttt{get\_config} reconstruction.}  For entries without a
  stored string (raw \texttt{cd\_values} configuration, files written
  before this RFC, or files written under a libver bound that forced the
  version-2 message), the filter's \texttt{get\_config} callback
  reconstructs a best-effort string from \texttt{cd\_values}.
\item \textbf{Raw \texttt{cd\_values} formatting.}  When neither source is
  available, the raw \texttt{cd\_values} are formatted as a fallback string
  using colon separators (e.g., \texttt{"cd\_values=1:0:0:1074921472"}).
  The colon separator avoids ambiguity with the comma-separated key=value
  grammar defined in \SectionRef{sec:param-format}---the fallback is a
  single key=value pair whose value contains colons, which is valid under
  the grammar.
\end{enumerate}

\verysubsection{Note on reconstructed strings (sources 2 and 3)}
\texttt{get\_config} reconstruction is inherently limited. The
\texttt{cd\_values} encoding carries opaque integer data, not a lossless
serialisation of a key-value string. For some filters (e.g., ZFP),
floating-point configuration values are quantised during conversion to
unsigned integers; the original value cannot be exactly recovered from the
stored integer, and the reconstructed string will reflect the rounded
value rather than what the user originally typed. Consumers should treat
reconstructed strings as informational only.  These caveats do \emph{not}
apply to source~1: a stored string is returned byte-for-byte as the user
supplied it.  Callers that need to distinguish an authoritative stored
string from a reconstruction can compare against
\texttt{H5Pget\_filter2} output or note whether the plugin was required;
the common case --- pipelines configured through the string API and
written without a restrictive libver bound --- always yields source~1.

\verysubsection{Note on \texttt{H5Pget\_filter2}}
The existing \texttt{H5Pget\_filter2} function returns the class
struct's \texttt{name} field.  In v2 plugins this is a free-form
debug comment; in v3 plugins it is the canonical name.  For v3
plugins, \texttt{H5Pget\_filter2} returns \texttt{name} directly from
the runtime registry when the plugin is loaded; otherwise it returns
the name stored in the pipeline message at filter-add time;
otherwise it falls back to the numeric filter ID formatted as a
decimal string.  Because the plugin's \texttt{name} is written into
the filter-pipeline message's name slot at filter-add time, the name
is available even when the plugin is not loaded.
\texttt{H5Pget\_filter\_params\_by\_idx} complements \texttt{H5Pget\_filter2}
by returning the parameter string rather than the filter name.

\verysubsection{Parameters}

\begin{itemize}
\item \texttt{plist\_id}---A dataset creation property list identifier.
\item \texttt{filter\_idx}---Zero-based index of the filter in the pipeline.
\item \texttt{params\_buf}---Buffer to receive the parameter string, or \texttt{NULL}
  to query size only.
\item \texttt{params\_buf\_size}---Size of \texttt{params\_buf} in bytes.
\item \texttt{params\_len}---On output, set to the length of the parameter string
  (excluding NUL), or \texttt{NULL} if not needed. Set even when \texttt{params\_buf}
  is \texttt{NULL}, enabling a size query.
\end{itemize}

\verysubsection{Returns}
Non-negative on success; negative on failure.


\subsection{Developer Helpers: Typed Parameter Lookup}
\label{sec:config-get-param}

Because the parameter string format is now TOML-typed, the library provides
typed accessor functions in \texttt{H5Zdevelop.h} rather than a single
string-returning helper.  All built-in filter \texttt{set\_config} implementations
use these functions.

\begin{minted}{c}
/* Key presence check (all types) */
htri_t H5Zconfig_has_key(const char *params, const char *key);

/* Typed accessors -- return htri_t: >0 found, 0 absent, <0 error */
htri_t H5Zconfig_get_int    (const char *params, const char *key,
                              int64_t  *out);
htri_t H5Zconfig_get_double (const char *params, const char *key,
                              double   *out);
htri_t H5Zconfig_get_bool   (const char *params, const char *key,
                              bool     *out);
htri_t H5Zconfig_get_str    (const char *params, const char *key,
                              char *buf, size_t *buf_size);
\end{minted}

\verysubsection{Description}
Each function searches the parameter string \texttt{params} for \texttt{key}
and writes the decoded value into \texttt{*out} (or \texttt{buf} for the string
accessor).  The \texttt{htri\_t} return type separates three cases cleanly:
found (\texttt{>~0}), absent (\texttt{0}), and error (\texttt{<~0}) ---
without pushing to the error stack for a merely absent optional parameter.

\texttt{H5Zconfig\_get\_str} follows the standard HDF5 size-query pattern:
\texttt{buf\_size} is in/out.  On entry \texttt{*buf\_size} is the buffer
capacity; on return it is set to the required byte count (excluding NUL).
Passing \texttt{NULL} for \texttt{buf} performs a size query only.  If the
buffer is too small, \texttt{H5E\_OVERFLOW} is pushed and the function returns
negative; the caller reallocates and retries.

Type mismatches (e.g., calling \texttt{H5Zconfig\_get\_int} on a key whose
value is a string) return negative with \texttt{H5E\_BADVALUE}.

These functions are placed in \texttt{H5Zdevelop.h} to limit the public API
surface.


\subsection{\texttt{cd\_values} Encoding Is Filter-Private (Non-Normative)}
\label{sec:cd-packing-convention}

Because the authoritative configuration is the parameter string persisted
on disk (\SectionRef{sec:pline-v3}), this RFC imposes \emph{no} normative
packing convention on \texttt{cd\_values}.  How a filter encodes typed
parameters into \texttt{unsigned int} slots is a private contract between
its \texttt{set\_config} and its execution callback; no other component
needs to decode it.  Earlier drafts of this RFC --- written under a
no-format-change constraint --- specified a normative cross-plugin slot
layout (little-endian split \texttt{double}s, length-prefixed string
chunks) so that \texttt{get\_config} could losslessly reconstruct the
configuration from \texttt{cd\_values} alone.  With the string stored
verbatim, that machinery is unnecessary and has been withdrawn
(\SectionRef{sec:type-tags-superseded}).

Two non-normative recommendations remain for filter authors:

\begin{itemize}
\item Encode wide values with \texttt{memcpy} of the IEEE\,754 or
  two's-complement representation rather than through lossy integer
  quantisation, so that \texttt{get\_config} can produce a faithful
  fallback string for entries configured through the raw
  \texttt{cd\_values} path (which stores no string,
  \SectionRef{sec:config-storage-rules}).
\item Keep the encoding stable across plugin versions, since
  \texttt{cd\_values} written by older releases of the plugin persist in
  existing files.
\end{itemize}


\subsection{Canonical \texttt{set\_config} Implementation Template}
\label{sec:set-config-template}

The two-pass \texttt{set\_config} protocol (\SectionRef{sec:callback-specs}) is
subtle. Plugin authors ensure identical \texttt{cd\_nelmts} on both passes.
The following template shows the recommended implementation pattern. All
built-in filter \texttt{set\_config} callbacks follow this structure and are
documented in \texttt{H5Zdevelop.h} as normative examples.

\begin{minted}{c}
static herr_t
my_filter_set_config(const char *params, unsigned *flags,
                     size_t *cd_nelmts, unsigned cd_values[],
                     size_t cd_values_size)
{
    /* ---- 1. Parse parameters (identical on both passes) ---- */
    int64_t level = 6;   /* default */

    if (params) {
        htri_t found = H5Zconfig_get_int(params, "level", &level);
        if (found < 0) return FAIL;
        if (found > 0 && (level < 0 || level > 9)) {
            H5Epush(..., H5E_BADVALUE, "level must be 0-9");
            return FAIL;
        }
    }

    /* ---- 2. Report element count (SAME on both passes) ---- */
    *cd_nelmts = 1;

    /* ---- 3. Populate cd_values only on the second pass ---- */
    if (cd_values != NULL) {
        /* cd_values_size is an ELEMENT count, not a byte count */
        if (cd_values_size < *cd_nelmts)
            return FAIL;               /* should not happen */
        cd_values[0] = (unsigned)level;
    }

    /* ---- 4. Optionally override flags ---- */
    /* (void)flags;  -- accept caller's flags unchanged */

    return SUCCEED;
}
\end{minted}

\verysubsection{Key invariants}
\begin{itemize}
\item \texttt{cd\_nelmts} is set to the same value regardless of whether
  \texttt{cd\_values} is \texttt{NULL} or non-\texttt{NULL}.
\item Parameter parsing is performed on both passes (not cached) to
  ensure the count is consistent.
\item If \texttt{cd\_values} is non-\texttt{NULL}, verify
  \texttt{cd\_values\_size >= *cd\_nelmts} before writing.
  \texttt{cd\_values\_size} is the number of \texttt{unsigned} \emph{elements}
  available, not a byte count.
\item Use the typed accessors (\texttt{H5Zconfig\_get\_int},
  \texttt{H5Zconfig\_get\_double}, etc.)\ rather than manual string conversion;
  locale independence and TOML type checking are handled by the accessors.
\end{itemize}

\textbf{Note on double parsing:} Because \texttt{cd\_nelmts} may vary depending on
the parameter values (not just their presence), the two-pass protocol requires
the callback to parse the parameter string twice.  Filters that wish to avoid
this overhead may report a fixed worst-case \texttt{cd\_nelmts} on both passes,
allocate that many slots on the stack, and fill unused trailing slots with a
sentinel value.  This is conforming provided the worst-case count is a genuine
constant---independent of the parameter string---so that both passes always
return the same value and the two-pass identity contract is satisfied.
The library does not mandate which approach is used.


\subsection{Pipeline-in-a-String API}
\label{sec:pipeline-string}

A convenience function that accepts a semicolon-delimited pipeline string
(e.g., \texttt{"shuffle; deflate, level = 9; fletcher32"}) is deferred to a
future release.  The semicolon character is reserved outside of quoted strings
(\SectionRef{sec:param-parser}) for this purpose.
\texttt{H5Pappend\_filter} (\SectionRef{sec:append-filter}) is the primary API.

\section{On-Disk Configuration Storage}
\label{sec:pline-v3}

This RFC introduces an on-disk format change: the validated parameter
string is persisted in \emph{canonical form}
(\SectionRef{sec:config-canonical-form}) --- first in the DCPL, then in a
new version~3 of the filter-pipeline object-header message
(\texttt{H5O\_PLINE\_VERSION\_3}) --- alongside the \texttt{cd\_values}
produced by \texttt{set\_config}.  The canonical form is the user's own
string with two value-preserving normalisations applied, so that the stored
bytes are guaranteed to be a valid TOML v1.0.0 document.  The stored
string, not a reconstruction from \texttt{cd\_values}, is the authoritative
human-readable representation of a filter's configuration.  \texttt{cd\_values} remain
exactly what they are today: the execution encoding consumed by the
filter callback.  Because the string is persisted independently,
\texttt{cd\_values} carry no round-trip obligation, and their internal
layout stays a private matter between a filter's \texttt{set\_config}
and its execution callback (\SectionRef{sec:cd-packing-convention}).

Because a format change is being made, it is made once and made
extensible: the version-3 entry ends in a list of self-describing
extension blocks (\SectionRef{sec:pline-v3-layout}), of which the
configuration string is the first.  Later attachments to a pipeline entry
--- the blob channel of RFC-HDFG-2026-003, name-only entries for
name-based lookup --- are new block types read by any version-3 library,
not new message versions that older libraries must reject wholesale.

Storing the string directly removes the two limitations that shaped
earlier drafts of this design, which were constrained to introduce no
format change:

\begin{enumerate}
\item \textbf{Plugin-free --- and library-free --- introspection.}  Tools
  such as \texttt{h5dump} read the stored string straight out of the
  pipeline message.  No plugin needs to be located, loaded, or trusted to
  reconstruct the configuration.  Because the stored bytes are canonical
  (\SectionRef{sec:config-canonical-form}), a reader that is not the HDF5
  library at all --- a pure-reimplementation reader such as jHDF or pyfive,
  decoding the object header directly --- can parse the configuration with
  a stock TOML parser.
\item \textbf{Exact round-trip of the configured value.}  The stored string
  denotes exactly the value the user passed to
  \texttt{H5Pappend\_filter}: the two canonicalising rewrites are
  bit-exact.  Floating-point formatting precision, quantisation inside
  \texttt{set\_config}, and packing-layout conventions no longer have any
  bearing on what introspection returns.
\end{enumerate}

\subsection{What Is Stored, and When}
\label{sec:config-storage-rules}

\begin{itemize}
\item \texttt{H5Pappend\_filter} with \texttt{H5Z\_PARAMS\_STRING}: after
  \texttt{set\_config} validates the string and produces
  \texttt{cd\_values}, the library retains the caller's parameter string
  verbatim in the DCPL pipeline entry.  A \texttt{NULL} or empty string
  (``no parameters'') stores nothing.
\item \texttt{H5Pappend\_filter} with \texttt{H5Z\_PARAMS\_CDVALUES},
  \texttt{H5Pset\_filter}, and all other legacy configuration paths: no
  string is stored.  Introspection for such entries falls back to
  \texttt{get\_config} reconstruction exactly as for files written before
  this RFC (\SectionRef{sec:introspection}).
\item \textbf{Filter names are not stored by this RFC.}  Third-party
  filters continue to use the version-2 name slot; built-ins continue to
  have no name on disk (\SectionRef{sec:class3-struct}).  Version~3 adds
  no name storage of its own.
\end{itemize}

\verysubsection{Why the canonical user string, and not a raw or
post-processed form}

Four candidate representations were considered for the stored string:

\begin{enumerate}
\item \textbf{The canonical user string (chosen).}  The user's own string
  with exactly two value-preserving normalisations applied: optional outer
  braces are stripped, and C99 hex-float literals are rewritten to
  \texttt{\%.17e} decimal.  Interior spacing, quote style, key case, and
  key order are preserved byte-for-byte.  See
  \SectionRef{sec:config-canonical-form} for why these two, and only these
  two, are applied.
\item \textbf{The raw user string.}  Rejected: the accepted input language
  is a \emph{superset} of TOML v1.0.0 in two respects
  (\SectionRef{sec:config-canonical-form}), so a raw payload is not
  guaranteed to parse with a stock TOML parser.  That defeats the purpose
  of persisting the string, which is to be readable without the HDF5
  library, not merely without the plugin.
\item \textbf{A parser-normalised re-serialisation} (keys lowercased,
  values re-emitted).  Rejected: re-serialising floating-point values
  reintroduces the very decimal-precision machinery
  (\SectionRef{sec:float-precision}) that storing the string is meant to
  make non-load-bearing.  The canonical form does \emph{not} re-serialise
  values; it rewrites only the one token form that TOML cannot express, and
  that rewrite is exact.
\item \textbf{The post-processing \texttt{get\_config} output} (``what the
  filter actually applied,'' including defaults).  Rejected as the
  \emph{stored} form: it depends on the quality of a plugin callback and is
  lossy for filters that quantise parameters.  That view remains available
  at runtime by calling \texttt{get\_config} when the plugin is loaded, so
  choosing the canonical string forfeits nothing.
\end{enumerate}

Defaults not present in the user's string are intentionally not baked into
the stored form: which defaults apply is a property of the filter version
that executes, and recording user intent keeps the stored configuration
meaningful across plugin upgrades.

\verysubsection{Canonical form of the stored string}
\label{sec:config-canonical-form}

Every constraint the filter profile places on parameter strings
(\SectionRef{sec:param-overview}) is a \emph{restriction}: \texttt{inf},
\texttt{-inf}, and \texttt{nan} are rejected; arrays, multi-line strings,
datetime values, and document-level tables are not accepted; length and
key count are bounded.  Those keep the accepted language a subset of TOML
v1.0.0, which is the safe direction --- anything accepted is still valid
TOML.

Two features go the other way and make the accepted language a superset:

\begin{itemize}
\item \textbf{Optional outer braces.}  \texttt{level = 6} is a valid TOML
  document, but \texttt{\{level = 6\}} is an inline table \emph{value} and
  is not a valid document on its own.
\item \textbf{C99 hex-float literals.}  \texttt{rate = 0x1.8p+1} is not
  valid TOML at all; the library accepts it only because it rewrites
  hex-float tokens to decimal before the TOML scanner
  (\SectionRef{sec:float-precision}).
\end{itemize}

Both are accepted on input, and both would otherwise reach the file
unchanged.  A reader handed those bytes and a stock TOML parser gets a hard
parse error --- not a silent misreading, but a failure nonetheless.  This
matters because the readers of this field are not only the HDF5 library:
pure-reimplementation readers such as jHDF and pyfive decode the object
header directly and never link \texttt{libhdf5}, and they are precisely the
consumers that benefit from a stored string rather than a plugin
reconstruction.  Normalising only one of the two would buy nothing, since
either alone is enough to break a stock parse.

The library therefore canonicalises the string before persisting it:

\begin{enumerate}
\item Strip optional outer braces and surrounding whitespace.
\item Rewrite C99 hex-float literals to \texttt{\%.17e} decimal.  This is
  bit-exact: \texttt{DBL\_DECIMAL\_DIG} is 17, so the decimal form recovers
  the identical IEEE\,754 \texttt{double}.  Hex-float text inside a quoted
  string or a comment is left alone.
\end{enumerate}

\begin{notebox}
\textbf{Guarantee.}  The bytes stored in \texttt{H5O\_PLINE\_EXT\_CONFIG}
are always a valid TOML v1.0.0 document, and are always valid input to
\texttt{set\_config}.  A conforming TOML parser can read a filter's
configuration out of any file this library writes, with no HDF5 code and no
filter plugin involved.
\end{notebox}

The cost is that the stored string is no longer byte-identical to the
caller's argument in these two cases: a caller who writes
\texttt{\{rate = 0x1.8p+1\}} reads back
\texttt{rate = 3.00000000000000000e+00}.  What is preserved is the
\emph{value}, exactly, which is the property the format change was made to
obtain.  Callers that need the original text of their own configuration
already have it.

\subsection{DCPL Retention and Property-List Machinery}
\label{sec:dcpl-retention}

The internal pipeline property gains a per-entry configuration string.
All property-list machinery handles it uniformly:

\begin{itemize}
\item \texttt{H5Pcopy} duplicates the string with the entry.
\item \texttt{H5Pencode}/\texttt{H5Pdecode} serialise and restore it, so
  the broadcast pattern recommended for Parallel HDF5
  (\SectionRef{sec:thread-safety}) preserves it.
\item \texttt{H5Pmodify\_filter} \emph{clears} the stored string for the
  modified entry: the caller has replaced \texttt{cd\_values} directly, so
  the string no longer describes the entry's configuration.  Introspection
  for that entry reverts to \texttt{get\_config} fallback.  Clearing is
  mandatory --- retaining a string that disagrees with the entry's
  \texttt{cd\_values} would make introspection actively wrong rather than
  merely approximate --- which is why
  \texttt{H5Pmodify\_filter\_by\_idx} (\SectionRef{sec:modify-filter})
  exists: it is the edit path that supplies a replacement string instead of
  discarding the old one.  Its \texttt{H5Z\_PARAMS\_CDVALUES} form clears
  the string for the same reason and on the same terms.
\item \texttt{H5Premove\_filter} discards the string with the entry.
\item \texttt{H5Ocopy} deep-copies the string alongside \texttt{cd\_values}
  when copying a dataset's pipeline message.
\item \texttt{H5Pequal} (via the pipeline property's comparison callback
  \texttt{H5P\_\_pline\_cmp}) does \emph{not} compare stored configuration
  strings.  Two entries with identical \texttt{id}, \texttt{flags}, and
  \texttt{cd\_values} compare equal whether or not either carries a
  string, and regardless of the strings' contents.  The rationale is that
  \texttt{cd\_values} determine I/O behaviour completely: two pipelines
  that agree on them will filter data identically, and reporting them
  unequal because one was configured as \texttt{"level=6"} and the other
  as \texttt{"level = 6"} would make \texttt{H5Pequal} sensitive to
  formatting.  This also keeps a round-tripped DCPL --- encoded, decoded,
  or read back from a file written under a restrictive libver bound ---
  equal to the original.  It is consistent with the existing treatment of
  \texttt{cd\_nelmts}-equivalent pipelines and deliberately inconsistent
  with the name slot, whose \texttt{strcmp} is pre-existing behaviour this
  RFC does not change (\SectionRef{sec:class3-struct}).
\end{itemize}

\subsection{Pipeline Message Version 3}
\label{sec:pline-v3-layout}

Each filter entry in the version-3 pipeline message carries the existing
version-2 fields followed by a list of self-describing \emph{extension
blocks}:

\begin{Verbatim}[fontsize=\scriptsize]
[existing v2 per-filter layout, field order unchanged]
  UINT16  filter_id
  UINT16  name_length        (third-party filters only; includes the NUL)
  UINT16  flags
  UINT16  cd_nelmts
  char    name[name_length]  (third-party filters only; NUL-terminated)
  UINT32  cd_values[cd_nelmts]

[new in v3: per-entry extension block list]
  UINT16  ext_count          (number of blocks that follow; 0 = none)

  ext_count repetitions of:
    UINT16  ext_type         (registered block type; see table below)
    UINT8   ext_flags        (bit 0 = critical; bits 1-7 reserved, zero)
    UINT8   reserved         (must be written as zero)
    UINT32  ext_length       (byte length of ext_data)
    uint8   ext_data[ext_length]
\end{Verbatim}

All other message fields --- including the version-2 name-slot rules for
built-in versus third-party filters (\SectionRef{sec:class3-struct}) ---
are unchanged from version~2.  An entry with \texttt{ext\_count = 0} is a
version-2 entry with two extra bytes.

Note that the version-2 field order interleaves the name: the name
\emph{length} is written immediately after \texttt{filter\_id}, but the
name \emph{bytes} come after \texttt{cd\_nelmts}, and
\texttt{name\_length} counts the trailing NUL.  That ordering is a
property of the existing format, not a choice this RFC makes; it is
reproduced above so that the extension list is understood to follow
\texttt{cd\_values} and nothing else.

\verysubsection{Why a block list rather than a fixed field}

The obvious encoding for this RFC in isolation appends two fields to each
version-2 entry: a length and the configuration string.  That encoding is
rejected because the configuration string is demonstrably not the last
thing that will need to be attached to a pipeline entry.  Two further
attachments are already specified or designed --- the binary blob channel
of RFC-HDFG-2026-003 (\SectionRef{sec:blob-future}) and the name-only
pipeline entries that soft-failure semantics for name-based filter lookup
require (\SectionRef{sec:future-name-lookup}) --- and under a fixed
layout each one costs a further message version.  Version~4 and version~5
would each be a fresh compatibility cliff: a library that shipped
version~3 support could not read a file that used only the later feature,
even though it understands everything else in the message.

Since this RFC pays for a format change once, it pays for an extensible
one.  A version-3 reader parses any block it does not recognise by length
alone and moves on, so a feature added later is readable by every library
that shipped version-3 support --- not only by libraries that shipped the
later feature.  The follow-on work named above therefore lands as new
block types within version~3.  No version~4 of the filter-pipeline message
is anticipated.

\verysubsection{Unknown block handling (normative)}

Bit~0 of \texttt{ext\_flags} is the \emph{critical} bit.  It tells a
reader that does not recognise \texttt{ext\_type} what to do:

\begin{itemize}
\item \textbf{Critical clear (0).}  Skip \texttt{ext\_length} bytes and
  continue.  The entry stays fully usable; only the information carried by
  that one block is unavailable, and introspection for it degrades exactly
  as it does for a version-2 entry.  Blocks carrying descriptive or
  introspective data --- both types defined by this RFC --- clear the bit.
\item \textbf{Critical set (1).}  Fail the dataset open with an error
  naming the unsupported block type and filter ID.  The reader must
  \emph{not} skip the block and proceed to filter data: the entry's
  configuration is incomplete without it, and falling back to
  \texttt{cd\_values} alone would silently produce wrong results.  A
  configuration payload stored out of line (\SectionRef{sec:blob-future})
  is the motivating case.
\end{itemize}

The critical bit is a property of the block type, fixed by whichever
specification defines that type; it is not a per-file choice, and a given
\texttt{ext\_type} is always written with the same value of bit~0.  The
bit exists so that a reader can make the correct decision about a type it
has never heard of --- which is the whole point of the framing.

Two further rules keep the list unambiguous.  Blocks are written in
ascending \texttt{ext\_type} order, so an encoder produces byte-identical
output for a given entry regardless of the order in which the library
populated it (this matters for the collective-write determinism
requirement in \SectionRef{sec:parallel}).  A block type not marked as
repeatable by its defining specification appears at most once per entry;
a decoder that sees a duplicate rejects the message as malformed rather
than silently taking the first or last.

\verysubsection{Registered block types}

Type codes are assigned centrally by The HDF~Group and recorded in
\texttt{H5Oprivate.h}:

\begin{center}
\begin{tabular}{llll}
\toprule
\textbf{Code} & \textbf{Name} & \textbf{Critical} & \textbf{Defined by} \\
\midrule
\texttt{0x0001} & \texttt{H5O\_PLINE\_EXT\_CONFIG} & no  & this RFC \\
\texttt{0x0002} & \texttt{H5O\_PLINE\_EXT\_BLOB}   & yes & reserved for RFC-HDFG-2026-003 \\
\texttt{0x0003}--\texttt{0xFFFF} & --- & --- & unassigned \\
\bottomrule
\end{tabular}
\end{center}

There is deliberately no private or experimental range.  A file carrying a
privately chosen code is indistinguishable from one carrying a code
assigned officially later, and the resulting collision would be
undiagnosable in the field --- the reader would parse foreign bytes as a
type it thinks it knows.  Projects that need a block type request one; the
cost of assignment is a line in a header.

\texttt{H5O\_PLINE\_EXT\_CONFIG} carries the canonical parameter string
(\SectionRef{sec:config-canonical-form}) as
UTF-8, not NUL-terminated and with no trailing NUL counted in
\texttt{ext\_length}.  At most one appears per entry.

\verysubsection{Size bounds}

\texttt{ext\_length} is 32-bit so that the framing is never itself the
binding limit on a future block type.  The effective ceiling is imposed
from outside: the object-header message size field is 16-bit, so an entire
pipeline message --- every entry, every block --- must fit within
64\,KiB.  A payload larger than that cannot live inline in any version of
this message and must be stored elsewhere in the file and referenced from
a block, which is precisely the shape the blob channel takes
(\SectionRef{sec:blob-future}).

One consequence worth stating precisely: widening
\texttt{H5Z\_CONFIG\_STRING\_MAX} (4096,
\SectionRef{sec:param-overview}) no longer requires a change to the
\emph{encoding}, because \texttt{ext\_length} is 32-bit where the earlier
fixed \texttt{config\_length} field was 16-bit.  It does, however, remain a
compatibility boundary: the decoder rejects an
\texttt{H5O\_PLINE\_EXT\_CONFIG} block whose \texttt{ext\_length} exceeds
\texttt{H5Z\_CONFIG\_STRING\_MAX}, so a file written under a raised cap
would not be readable by an already-released version-3 reader.  Raising the
limit is therefore a versioned, coordinated change to the format's
acceptance rules, not a purely API-level policy adjustment.

\subsection{When Version 3 Is Written}
\label{sec:pline-v3-gating}

The message version is selected per pipeline message at object-header
encode time (e.g., \texttt{H5Dcreate}), following the standard
\texttt{H5Pset\_libver\_bounds} gating used by every versioned HDF5
format feature:

\begin{enumerate}
\item If \emph{no} entry in the pipeline carries an extension block, the
  library writes version~2 (or version~1, per the existing rules) ---
  byte-identical to the output of an equivalent \texttt{H5Pset\_filter}
  program, at any libver bound.
\item If at least one entry carries an extension block \emph{and} the
  file's libver upper bound admits version~3 (i.e.\ is at least
  \texttt{H5F\_LIBVER\_V300}), the library writes version~3.
\item If an extension block is present but the libver upper bound is below
  \texttt{H5F\_LIBVER\_V300}, the library writes version~2 and omits the
  blocks.  The
  file is byte-identical to pre-RFC output; execution semantics are
  unaffected because \texttt{cd\_values} are complete on their own, and
  introspection degrades to the \texttt{get\_config} fallback.  The
  downgrade is silent, consistent with how libver bounds gate other
  format features; applications can detect it by re-opening the dataset
  and querying \texttt{H5Pget\_filter\_params\_by\_idx}.
\end{enumerate}

Rule~1 preserves the adoption story that motivated earlier drafts:
existing programs, and new programs that use only the raw
\texttt{cd\_values} form, produce files indistinguishable from today's.
Only callers who opt into string configuration --- and do not bound the
file format below the shipping release --- produce version-3 messages.

Stating the rules in terms of extension blocks rather than stored strings
is what lets a later block type inherit this gating unchanged.  A future
feature that attaches a block to an entry makes that pipeline message
version~3 by the same Rule~2, and is suppressed by the same Rule~3 under a
restrictive libver bound, without any new gating logic.  Rule~3's silent
downgrade is safe only for non-critical blocks, however: a critical block
(\SectionRef{sec:pline-v3-layout}) carries information the entry cannot be
interpreted without, so dropping it would corrupt the caller's intent
rather than merely degrade introspection.  The specification that defines
a critical block type must therefore state that a restrictive libver bound
is a hard error for entries carrying it, not a silent downgrade.  Both
block types defined by this RFC are non-critical and downgrade silently.

\verysubsection{Where the gating lives}

The three rules above are not a new mechanism.  HDF5 already selects the
pipeline-message version through a table and a setter in
\texttt{src/H5Opline.c}:

\begin{minted}{c}
/* Existing: maps each libver bound to the maximum pipeline message
 * version it admits.  One row per H5F_libver_t. */
static const unsigned H5O_pline_ver_bounds[] = {
    H5O_PLINE_VERSION_1,       /* H5F_LIBVER_EARLIEST */
    H5O_PLINE_VERSION_2,       /* H5F_LIBVER_V18     */
    H5O_PLINE_VERSION_2,       /* H5F_LIBVER_V110    */
    H5O_PLINE_VERSION_2,       /* H5F_LIBVER_V112    */
    H5O_PLINE_VERSION_2,       /* H5F_LIBVER_V114    */
    H5O_PLINE_VERSION_2,       /* H5F_LIBVER_V200    */
    H5O_PLINE_VERSION_LATEST   /* H5F_LIBVER_LATEST  */
};
\end{minted}

\texttt{H5O\_pline\_set\_version()} raises the message version to the
file's \emph{low} bound, then errors if the result exceeds the \emph{high}
bound (\texttt{``Filter pipeline version out of bounds''}).  This RFC
changes that function in exactly two ways:

\begin{enumerate}
\item The version required by content is computed as version~3 if any
  entry will emit at least one extension block, and by the existing rules
  otherwise.
\item When the required version exceeds the high bound, the function no
  longer errors unconditionally.  It first drops the blocks that are
  droppable --- every non-critical block --- and recomputes.  If the
  requirement falls to version~2, encoding proceeds with the blocks
  omitted (Rule~3).  If a critical block remains, the existing
  out-of-bounds error stands, because that block cannot be dropped
  without changing what the file means.
\end{enumerate}

Version~3 is admitted by the \texttt{H5F\_LIBVER\_V300} bound.  The
\texttt{V200} row stays at version~2: \texttt{H5F\_LIBVER\_V200} already
exists and appears in released files, so changing what it admits would
retroactively alter the meaning of a bound callers have already written
against.  The table therefore gains one row:

\begin{minted}{c}
    H5O_PLINE_VERSION_2,     /* H5F_LIBVER_V200 */
    H5O_PLINE_VERSION_3,     /* H5F_LIBVER_V300 -- new row  */
    H5O_PLINE_VERSION_LATEST /* H5F_LIBVER_LATEST           */
\end{minted}

\noindent with \texttt{H5O\_PLINE\_VERSION\_LATEST} bumped to~3.  This
RFC introduces no libver constant of its own: \texttt{H5F\_LIBVER\_V300}
is the format bound of the 3.0 release, which that release defines for
its own reasons and this feature merely occupies.  Beyond the table row
and the \texttt{H5O\_pline\_set\_version()} changes above, nothing else in
the library's version-gating machinery is touched.

\subsection{Reader Compatibility}
\label{sec:pline-v3-readers}

A library that predates version~3 fails to decode a version-3 pipeline
message: the existing version check in the pipeline-message decoder
rejects unknown versions, surfacing as a clear dataset-open error.  This
is the standard consequence of opting into a newer format feature (as
with, e.g., virtual datasets), and \texttt{H5Pset\_libver\_bounds} is the
standard user-controlled escape hatch for producing files that older
readers must open.  No superblock feature flag is required; the message
version field carries the signal.

Within a v3-capable library, the stored string places no new demands on
plugins: a dataset whose pipeline message is version~3 is filtered by v2
plugins exactly as before, since \texttt{cd\_nelmts} and
\texttt{cd\_values} are precisely what \texttt{set\_config} (or the
caller) produced.

\verysubsection{Forward compatibility within version~3}

The version check above is a cliff, and it is the only one this design
accepts.  Beyond it, compatibility is per-block rather than per-version.
A library that ships version-3 support reads every later version-3 file:
block types it knows it interprets, non-critical block types it has never
heard of it skips by length, and critical block types it does not
recognise it rejects with a specific error.  Concretely, a library
shipping only this RFC opens a file written by a library that also ships
the blob follow-on: it reads the configuration strings and names, and ---
because the blob block is critical --- fails cleanly and informatively on
exactly those datasets whose filters genuinely need the blob, rather than
failing on the whole file or, worse, filtering data with an incomplete
configuration.

This is the property that a fixed-field layout could not provide: there,
the same file would have been version~4, and the version check would have
rejected it outright even though the reader understood everything in it
that mattered.

\subsection{Superseded Alternative: Per-Slot Type Tags}
\label{sec:type-tags-superseded}

An earlier design direction kept \texttt{cd\_values} as the only
persisted configuration and appended a per-slot type-tag array
(\texttt{uint8} per slot) to the pipeline message so that readers could
reconstruct typed values from packed slots without the plugin.  That
approach required a normative cross-plugin packing convention, byte-order
rules for split 64-bit values, schema plumbing to emit correct tags, and
still yielded only a reconstructed --- not authoritative ---
configuration.  Since it costs a format change either way, this RFC
stores the self-describing string instead; the type-tag design is
superseded and no packing convention is normative
(\SectionRef{sec:cd-packing-convention}).

\subsection{Future Work: In-File Blob Configuration Storage}
\label{sec:blob-future}

Some compressors require configuration data larger than the 4096-byte
parameter-string limit (\SectionRef{sec:param-overview}) or the
65535-element \texttt{cd\_values} limit --- for example, pre-processed
source for a JIT-compiled filter module, or a reference to a spatial mask
stored as a separate dataset.  These cases were raised by @robertu94
during the community review of this RFC (HDFGroup/hdf5\_plugins\#255; see
\texttt{LIBPRESSIO-FEEDBACK.md} in this repository) and are addressed by a
follow-on RFC (RFC-HDFG-2026-003), which specifies a binary blob channel:
three new \texttt{H5Z\_class3\_t} callbacks
(\texttt{write\_blob}/\texttt{read\_blob}/\texttt{close\_blob}), a new
\texttt{H5Pappend\_filter\_blob} API, and on-disk storage for the blob
alongside the dataset's pipeline message.

That storage is the first consumer of the extension framing defined here.
The blob bytes live in a global-heap object; the pipeline entry carries
only a locator, as the reserved critical block type
\texttt{H5O\_PLINE\_EXT\_BLOB} (0x0002,
\SectionRef{sec:pline-v3-layout}).  Three consequences follow, and they
are the reason the framing is worth its two-byte-per-entry overhead:

\begin{itemize}
\item \textbf{No version~4.}  RFC-HDFG-2026-003 adds a block type, not a
  message version.  It inherits this RFC's encoder/decoder branching,
  \texttt{H5O\_pline\_ver\_bounds[]} row, libver gating, and copy/delete
  handling unchanged.
\item \textbf{Release timing is not forced.}  Both RFCs currently target
  the same release (3.0), and the blob feature's \emph{callbacks} must
  ship with its \emph{block type} --- they are useless apart.  But neither
  is coupled to the release that introduces version~3, so if the blob work
  slips it becomes a later block type rather than a blocked feature or a
  second message version.
\item \textbf{Safe partial readers.}  A library with version~3 but without
  blob support reads the configuration strings in such a file and rejects
  only the blob-bearing entries, by the critical-bit rule
  (\SectionRef{sec:pline-v3-readers}).
\end{itemize}  Because
\texttt{H5Z\_class3\_t} has not yet shipped as of this RFC, no fields are
reserved for it here; an earlier draft reserved three \texttt{void~*}
placeholders for this purpose, but that approach was dropped because
reserving an opaque placeholder does not avoid the struct-version bump the
feature needs once real callback signatures are decided --- it only defers
the decision.  RFC-HDFG-2026-003 adds the real, fully-typed callbacks
directly to \texttt{H5Z\_class3\_t} if it has not yet shipped by the time
that RFC is adopted, or to a new \texttt{H5Z\_class4\_t} otherwise.
